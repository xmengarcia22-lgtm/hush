## 1. Goals and non-goals

**Goals**

1. Keep every message, media file, group name and contact list end-to-end encrypted on the client, exactly as today.
2. Store as little metadata as the app can function with. In particular the server must never hold a plain list of who is in which chat, who talks to whom, or which usernames share a device.
3. Never log or store IP addresses.
4. Keep the client's existing database call shape so that the 122 call sites in index.html keep working behind a new adapter.
5. Be small enough for one person to run: one process, one database file, one reverse proxy.

**Non-goals for this version**

- Hiding activity timing or message sizes from the server.
- Hiding, from a live attacker inside the running server, which connection does what. Only durable storage is protected against that attacker.
- Network-level anonymity (Tor, mix networks).
- Push notifications, offline caching, multi-server scaling.
- Protecting against a malicious server that ships altered JavaScript to the browser. See 10.6 for the option that addresses this.
- Voice and video calls. Deferred, not excluded: they are stage 10, after launch, and section 16 lists what the earlier stages must leave open for them. Audio messages are not deferred; they are ordinary encrypted media attachments and arrive with stage 6.

## 2. Vocabulary

| Term | Meaning |
|---|---|
| handle | A username, lowercase, `^[a-z0-9_]{3,20}$`. Public. |
| account keys | A user's long-term P-256 key pairs: one ECDH, one ECDSA. The public halves live in the directory. Already exist in the client. |
| device keys | Per-device P-256 pairs that never leave the device. Listed and signed in the directory entry under `devs`. Already exist. |
| chat | A DM, group or channel. Identified by a chat id, `cid`. |
| epoch | A numbered version of a chat's symmetric key: 0 to 31 in a group or DM, 0 to 2^31−1 in a channel (release 91). Already exists. |
| chat key | The 32-byte AES-GCM key of one epoch. Wrapped per device in the chat record. Already exists. |
| tag | A 22-character pseudonym for a member in one chat and epoch, derived from the chat key. Already exists (`memTag`). |
| room keys | New. Bearer secrets that prove to the server that you may act on a chat: member key, admin key, owner key. The server stores only their hashes. |
| sealed | Encrypted with a chat key so that the server sees only ciphertext. |
| mailbox | New. A per-handle drop box for small sealed notices such as "you were added to chat X". |
| vault | The user's encrypted settings and contacts blob at a blind address. Already exists. |
| proven handle | The handle a WebSocket connection has proved it holds, by signing a server challenge with the account ECDSA key. |

## 3. Architecture

```
Browser (index.html + adapter)
   │  wss://<domain>/ws        one WebSocket: all reads, writes, live updates
   │  https://<domain>/drop    one unauthenticated POST per mailbox drop
   ▼
Caddy  (TLS, HSTS, static files from /srv/hush/www, no access log)
   │  127.0.0.1:8080
   ▼
Node 22 service  (single process, `ws` + Node's built-in `node:sqlite`, WebCrypto for signature checks)
   │
   ├── /var/lib/hush/hush.db    documents, chats, mailbox, directory, search
   ├── /var/lib/hush/media.db   encrypted media chunks
   └── /etc/hush/addr.key       server secret for keyed hashing of blind addresses (not in the DB)
```

- One WebSocket per browser tab. The connection holds in memory: at most one proven handle, the set of chats it has opened with a room key and at which level, its subscriptions, and its rate-limit buckets. None of this is written to disk. A restart drops it all and clients transparently reconnect.
- Mailbox drops go over a separate HTTPS POST that carries no session, so the server's own session state never associates sender and recipient.
- The static app is served from the same origin as the API, so the Content-Security-Policy only needs `'self'` plus the explicit `wss://<domain>` entry.
- The service listens only on localhost. Caddy is the only thing exposed on 80 and 443. SSH is key-only.

## 4. Identity plane: who you are to the server

Used only for things that are yours by name: your directory entry, search entry, phone lookup entry, presence, mailbox. Chat content never uses it.

### 4.1 Proving a handle

1. Client sends `hello`. Server replies with a 32-byte random `nonce`, the server time, and limits.
2. Client sends `prove { h, sig, dev?, pub? }` where `sig` is an ECDSA P-256 / SHA-256 signature (raw r||s, base64 or base64url) over the UTF-8 string `hush-session-v1|<nonce>|<h>|<dev or empty>`.
3. The key that must have signed depends on the frame:
   - with `dev`, the signing key of that device as listed under `devs` in `directory/<h>`, provided the entry's own signature chain verifies up to the account key (the same check the client's `verifiedDevs` does). This is the normal case for a device that is already on the profile.
   - without `dev`, the account signing key in `directory/<h>`.
   - if `directory/<h>` does not exist (sign-up), `pub` must be present and the signature is verified against it. The connection is then marked as "may create `directory/<h>` with `sig == pub`".
4. On success the connection is marked as acting for `h`. Exactly one handle per connection. To switch accounts the client opens a new connection; this keeps two of a user's handles from ever meeting in one server-side session object.

The client tries its device key first and falls back to the account key when the device is not listed yet (a first login, or a restore from recovery words), which is also how it publishes that device entry afterwards. The nonce is valid for two minutes and is consumed by a successful proof. A connection may prove once; a failed proof counts toward a per-address bucket (see 9.4), ten failures in ten minutes earn a pause.

### 4.2 What a proven handle may do

| Path | get | set / create | update | delete |
|---|---|---|---|---|
| `directory/<h>` | anyone, rate-limited (the sign-up screen checks availability before an account exists) | only `h`, doc.handle == h, doc.sig == proving key | only `h`; `ecdh`/`sig`/`kv` may change only if `kv` increases and the connection proved with the account key (not a device key); `prev` never, the server writes it (below); a tombstone (4.7) never | never; `account.delete` turns it into a tombstone (4.7) |
| `search/<h>` | query only, see 7.6 | only `h`, doc.h == h | only `h` | only `h` |
| `presence/<h>` | anyone proven, batched | only `h` | only `h` | only `h` |
| `phones/<hash>` | nobody: matching is off, 12.4 | nobody | nobody | only stored doc.handle |
| mailbox of `h` | pull / ack only by `h` | drop by anyone, see 6 | – | ack by `h` |

The server reads the `devs` entries for one purpose only: to check a device-key proof. It never stores anything about devices beyond those signed entries on the profile. Until stage 4 lands, everything under `channels/` requires a proven connection and nothing more.

**Key history (release 21).** When an account's keys change (`kv` rises; 14, item 15) the server itself appends the old signing key and its own time to the entry's `prev`: a list of at most eight `{ sig: {x, y}, until }`, the oldest dropped first. Clients never write it: a `set` or `update` that would change it is refused with `denied`, a `set` that leaves it out keeps the stored one, and a new entry may not bring one. Every device uses it to check messages signed before the change (`verifyBy`: an old key is accepted for a post, a sealed service note or a signed invitation note dated up to a minute after its `until`, and the result says so; a service note so verified is shown but never acted on; reactions, reads and typing take the current key only). For a contact whose key the device pinned, only the keys it pinned before count as history (kept at acceptance in the vault's pins), never the profile's `prev` alone, so a server can't vouch for a key the contact never had. A key change raises `kv` by exactly one, brings a new signing key, and is taken only from a connection proven with the key on record. Because a proof is checked asynchronously, `prove` reads the entry again afterwards and refuses with `denied` when its `sig` or `kv` changed in between, or when a free name was created in between; a successful proof records the key version it was made against, and the reply carries `kv`. When `kv` rises, every other connection proven for that handle holds the old keys and is closed with code 4401 `keys changed` (7.2); the connection that wrote the change is marked up to date. A sign-up proof is a reservation, not an account: when the profile is created over another connection, the reserving connection is closed with 4401 `username taken`.

### 4.3 Collections that need no proof

Five collections are addressed by secrets the client derives itself, so knowing the address is the credential. They are reachable before `prove`, which the sign-in, recovery and device-link flows require, and are rate-limited per address bucket and per path (9.4). At rest their addresses are keyed-hashed (8.3).

| Path | get | set / create | update | delete |
|---|---|---|---|---|
| `accounts/<loc>` | anyone | anyone, if absent | never | anyone |
| `logins/<tag>` | anyone | anyone, if absent (from release 20 pages reserve nothing: the rows are the email and phone logins of accounts from before) | never | never |
| `linkreqs/<tag>` | anyone | a new device, before signing in: its link ask, naming no account, only at the address its code's secret makes, counted per address (release 58); a signed-in account: its own link offer, only at the address the offer's name makes (14.14) | an ask: any signed-in account answers it once (`ok` or `no`), naming itself; an offer: the device that read the code claims it once, and only the account that opened it answers (9.3); at a login's tag, nobody from release 16 | an ask: anyone (the asker gives up, or whoever clears it once answered); an offer: the account that opened it, or the new device once answered; at a login's tag, nobody |
| `vault/<id>` | anyone | anyone | anyone | never, except by `account.delete` (4.7) |
| `backup/<id>` | anyone | anyone, naming the version it merged (9.3, release 19) | never (from release 19) | anyone |

### 4.4 Removed from the old model

`owners/*`, `owners/*/devices/*`, `uids/*` and the `_uid` / `_by` stamps on every write are gone. The server rejects any document that contains a key beginning with `_`.

### 4.5 Password boxes and the login gate

A password box holds the account's keys, sealed with a key stretched from the password (PBKDF2-SHA-256, 600,000 rounds; the second half of the 512-bit output). The first half, hashed, is `x`. Until release 9 the box lived at `accounts/<x>`, so anyone could test a password guess by reading an address, with no limit per account, since the server could not tell which login an address belonged to.

From release 9 the box lives at `accounts/<HMAC-SHA-256(gate key, "hush-login-gate-v1|" + t + "|" + x)>`, where `t` is the login's tag (`SHA-256("hush-login-v1:" + username)`; until release 20 an account could also log in with the email address or phone number given at sign-up, each with a box of its own, and accounts from before keep those boxes) and the gate key is the server's `addr.key`. Only the server can make that address: the page asks with `login.gate {t, x}` and gets `{loc}` back. Every ask that finds no box is counted against `t`, whoever asks (`pwMissesPerLogin`, 10 an hour); asks that find the box are not counted, so a person who knows their password is never charged for it. From release 15 two more asks are not counted, and prove nothing: one that lands on an address whose box this login had until it was deleted (a password change deletes the old boxes; the server remembers those addresses, under its key, for 30 days, `boxGoneMs`), and the same address asked again within the hour. Neither is a new guess; every new wrong guess still counts, and the answer is the same in every case. While a login is out of tries every answer waits, the right password included, so the wait says nothing about which guess was right. Someone who steals the database without `addr.key` can no longer test guesses offline at all; with `addr.key` (or as the server) they still can, which is why an owner or admin of a group or channel needs a password of 12 characters or more (4.6).

Trade-off, stated plainly: the server now learns, when a box is opened or saved, which login tag the box belongs to. It could already see this on the live connection (the page reads the reservation and the box together); now it is a property of the address. Separate logins of one account still have separate, unlinked boxes.

From release 16 no way in depends on the box addresses in the account’s settings (14.14): linking a device needs no box, and nothing looks a saved address up at the gate, so settings left out of date by a password change on another device never cost a wrong-password try and never lead to a password being asked for. A device that logs in with the password puts that login’s right address back in the settings quietly, for every device. Saving the settings keeps the box addresses another device saved after a password change.

Boxes from before the gate are moved the first time they are opened (`findBox`: read `accounts/<x>`, write it behind the gate, delete the old one), and a signed-in device moves the boxes of all its logins on its next load, without the password. Until a box has moved, its old address can still be guessed without a limit: accounts with no device that loads release 9 stay exposed this way until they log in once.

**Recovery boxes are not behind the gate.** Recovery words (the `HUSH RECOVERY` block of `app/crypto.js`) are made on the device from a list of 1,024 words and stretched the same way (PBKDF2-SHA-256, 600,000 rounds, 512 bits): the first half, hashed, is the address `accounts/<loc>`, the second half the AES-GCM key of a box holding the account's keys. No server key is involved, so a copy of the database is enough to test guesses offline; the words are therefore long and salted per account. From release 24 a new set is 12 words (120 bits), salted with `SHA-256("hush-recovery-salt-v2:" + username)` and sealed with the additional data `hush-recovery-v2`, so a restore asks for the username with the words (the login screen's username fills it in). The salt is worked out on the device; nothing new is stored or sent. Sets made before (v1) are 6 words (60 bits) under one salt shared by every account (`SHA-256("hush-recovery-salt-v1")`, additional data `hush-recovery-v1`), so one stolen database could be attacked for everyone at once. They keep working, without the username, until replaced: the page reads exactly 12 or 6 words and refuses any other count, only ever makes 12, counts a 6-word set as set up, and asks (a dismissable banner, the Settings row, a note after a restore with them) for new words. Making new words deletes the old box once the quick check passes (until then the old words keep working, and removing a device deletes it too), so the weak one stops existing. The device's record of the words (`hush:recovery:<handle>` and its vault copy `rec`) carries `v: 2` for the new kind; no marker means the older kind.

### 4.6 Power roles need a secured account (release 9)

Passwords for everyone are at least 8 characters, not all lowercase letters, not common, and not containing the person's own username, email or number. An owner or admin of a group or channel holds keys to other people's chats, so they need a stronger password: 12 characters or more, passing the same checks.

The server never sees a password, so it can't check one. Instead the page sets the account's secured mark, `secure/<h>` = `{ts}`, once it has seen a strong password for the account: at sign-up, at log-in, at a password change, or in the prompt below. Only the account can set it, it is never changed or removed, and nobody can read it but the server, so nobody learns whose password is weak. To keep that true, the server half (live since release 96) refuses an `update` or a `delete` of the mark from everyone, the account itself and a connection that is not signed in included, with `denied` ("this mark is read by the server only"), before it reads anything stored. So the answer is the same whether or not a mark exists, and nobody can test whose account has one (5.4). Before release 96 the server answered by what is stored. A changed page could set the mark without a strong password; that weakens only its own account.

The server enforces it in the only two places a connection gains a power level: `chat.create` of a group or channel is refused with `secure`, and `chat.open` with an owner or admin key opens at member level and answers `held: "owner" | "admin"`. Every owner or admin action checks the connection's level, so the tools of an unsecured owner or admin wait. A channel's sealed member and blocked lists (5.3) still reach such a connection, by the key it proved. Its read marks do not, because those go by the level the connection holds (5.4): it reads none, and it can update or delete none either. That covers every way into a role: creating, being promoted (the new admin's device opens with the admin key), holding a role from before release 9, and a new device of the account. Ownership can't be handed over in this version (5); a hand-over would go through `chat.open` too. `powerNeedsSecure: false` turns the rule off for development and tests only: a server running with `NODE_ENV=production` ignores it, so there the rule is always on.

The page asks at that moment, only when the account isn't secured: "Secure your account", naming the role and the chat ("You're now an admin of …. Admins hold the keys to this channel, so your password needs to be stronger"), with a suggestion to turn on the app lock. The prompt asks for the current password first ("Already strong? Just re-enter your current password."): if it is 12 characters or more, not all lowercase letters and not on the built-in list of common passwords, the account is marked secured and the password stays as it is. Only a current password that is too weak opens the fields for a new one, which must also pass the usual rules for choosing a password. Skipping (Not now, the close button, or Back) means: a new group or channel is not created; a role already held stays paused, read and post as a member, asked about again on the next load. Once secured, the page opens the paused chats again and gets the level its keys give.

The highest tier a person has held (none, admin, owner) is kept in their encrypted vault (`prefs.tier`), so the server never sees it. When it climbs past the best so far, the page fires `hush:tier-up` on `window` with `{tier}`, the hook for an upgrade card. A device of an account from before release 9 records the current tier silently the first time.

### 4.7 Deleting an account

Deletion is instant and can't be undone. The page asks for the password or the recovery words first; that check is the page's, not the server's (SECURITY.md).

**What the page erases first**, because only it can find these (their addresses come from secrets the server never sees): the password and recovery boxes, the message backup, the search entry, phone entries, the chats it owns; and it leaves its groups and channels. Then, as the last step, it sends `account.delete {vault}` (7.1) over a connection proven with the account key (4.1), naming its vault's id, which it alone can derive. A device-key proof or a sign-up proof is refused with `denied`, as is a connection proven against keys that have since changed, an account that doesn't exist or is already deleted; `unauth` before any proof; `invalid` for a malformed vault id, and then nothing is erased.

**What the server erases**, in one transaction: `vault/<vault>` (the only way a vault is ever deleted: a client `delete` is still refused, 4.3); every note in `inbox/<h>/c`; `secure/<h>` and `search/<h>`; every `phones` entry whose `handle` is `h`, and every retired `recovery` record and link offer (`linkreqs`) whose `h` is `h`; the block tags of `h` in every chat (5.6), its member card in every channel and its wrap counts (5.6, release 91), and the reports `h` sent (8.7), found by working their keyed tags out again; and, from memory, the presence row and the mailbox's drop allowance. `directory/<h>` becomes a tombstone. The reply `{ok}` goes out, then every connection proven for `h`, the asking one included, is closed with 4410 `account deleted` (7.2).

**The tombstone** is `{ handle, gone, ecdh, sig, kv, prev? }`, `gone` being the server's time of deletion. It keeps only the public keys and the key history (4.2), so everyone's app can still check the messages the person signed; name, display name, bio, photo, devices, `findable`, `requests` and everything else are dropped. Anyone may still read it (that is how apps learn the account is gone). Nobody writes over it: `set`, `update` and `delete` on it are refused with `denied`, and no client may write `gone`. The username is never free again: `prove` as `h`, with any key, and a sign-up as `h` are refused with `gone`, decided before any signature is checked, so the kept keys sign nobody in. `POST /drop` to `h` answers exactly as for a name that doesn't exist. A tombstone is no account for `report.send` and `report.list`. `login.gate` (4.5) still answers for the account's login tag: it finds no box, since the page deleted them, and answers as it does for any login. A `logins/<tag>` reservation from before release 20 holds only a time, so it can't be told to be this account's and stays.

**What stays**: the messages the person sent, in other people's chats, which apps show under "Deleted account"; the public keys and the username, for good; copies of public-channel posts in reports other people sent (8.7), which hold the post as stored and are not tied to the account; tags in chats (reactions, read marks) that the server can't tie to anyone, except, since release 97 (5.7), a channel's reaction and vote rows, whose slot the server can work out again from the username it keeps; and the nightly encrypted backups (8.6), which hold the erased records until they rotate out, up to 7 days.

## 5. Capability plane: room keys

Used for everything under `channels/<cid>`. The server never learns who is in a chat; it learns that the requester holds a secret for it.

### 5.1 The three keys

| Key | Scope | Derived from | Who holds it |
|---|---|---|---|
| member key `M_e` | one chat, one epoch | the epoch's chat key | every member device that can open epoch `e`; for public channels, anyone, because `openKeys` publishes the chat key |
| admin key `A` | one chat | a random 32-byte admin secret, wrapped to admins' devices in `akeys` | owner and admins |
| owner key `O` | one chat | the owner's private per-account secret `own`, made at sign-up and carried in the login box, the recovery box and the device handoff (accounts from before stage 7 have none and derive it from the signing private key, as before; a key replacement, 14 item 15, gives every account a fresh `own`) | owner only, recomputable on any of the owner's devices |

Derivations, all HKDF-SHA-256 with 32-byte output, encoded base64url (43 characters):

```
root_e  = HKDF(ikm = chatKey_e,          salt = "hush-caproot-v1", info = cid + "|" + e)
M_e     = HKDF(ikm = root_e,             salt = "hush-cap-v1",     info = "member")
A       = HKDF(ikm = adminSecret,        salt = "hush-cap-v1",     info = "admin|" + cid)
O       = HKDF(ikm = ownerSigPriv.d,     salt = "hush-cap-v1",     info = "owner|" + cid)
```

For a DM at epoch 0, where today's chat key is derived on the fly from the two account ECDH keys and never exported, `chatKey_0` in the formula above is the raw 256-bit ECDH shared secret between the two account ECDH keys. Both members can compute it; the server cannot.

The server stores `sha256(M_e)` for the current epoch only, `sha256(A)` and `sha256(O)` as lowercase hex. It never stores a key itself. Rotating to a new epoch replaces the member hash and immediately invalidates the old one.

As built: a DM also keeps the hash of its epoch-0 member key as a base key (`cap_b`), beside the current member hash. Either person can always derive it from the two account keys, so a device that lost its chat keys (a restore from recovery words) can still open the DM and rotate it to a fresh epoch. Without this, nobody could ever heal a DM.

**Replacing a base key or an owner key (release 21).** When an account's keys are replaced (14, item 15) the old shared secret still derives the old base key, so a removed device could open every DM with it. `chat.rebase { cid, cap }` replaces a DM's base key hash with the one the new keys give. Only a connection that opened the DM with its current member key (the one the last `chat.rotate` set, not the base key) may do it, and only once the DM has a key of its own (epoch 1 or later), so a device holding nothing but the old shared secret can't rebase a DM away from its owner; every other connection's level for the DM is evicted. Either person in the DM can do it (the server knows no members), so whoever holds the current member key first decides the base key: the page therefore re-keys its chats right after publishing the new account keys, and a chat whose keys were replaced from elsewhere first is named in the summary as lost ("Start new chats with the same people."). The pages keep the shared secret from before the change in their chat-key store (label `b`), so the DM's history stays readable, and try the old base key last when opening (12). `chat.owner { cid, cap }` replaces a group's or channel's owner key hash: owner level only, not for DMs, every other connection evicted. The owner key comes from the account secret `own`, which a key replacement rotates, so the owner moves it over; this is not a hand-over (5.6).

### 5.2 Opening a chat on a connection

`chat.open { cid, cap }` hashes `cap`, compares against the chat's three hashes and marks the connection as holding the matching level for `cid`: `member`, `admin` or `owner`. Levels are ordered; owner implies admin implies member. Later frames for that `cid` need no key. When the chat rotates, the server evicts every connection's level for that `cid` except the rotator's and pushes `{ t: "evict", cid }`; clients re-derive and re-open, or treat themselves as removed.

### 5.3 Chat record and the "no names" rule

Nothing under `channels/<cid>` may contain a handle in plaintext. The server enforces a denylist of field names on create, set and update for every chat whose `visibility` is not `public`: `members`, `owner`, `admins`, `banned`, `from`, `by`, `to`, `req`, and any key starting with `_`. Public channels may carry `owner` and `admins` because they are public facts of a public channel, and `name`, `desc`, `photo` in the clear so that they can be browsed.

Fields of the chat record:

| Field | Plain or sealed | Notes |
|---|---|---|
| `type` | plain | `dm`, `group`, `channel`. Needed by the server to pick the posting level. Since release 107 a record is created only at an id of its own kind (`d` a DM, `g` a group, `c` a channel; `invalid` otherwise); a record from before is not touched. |
| `visibility` | plain | `private` or `public`. Since release 107 `public` only in a channel: a DM or a group is neither created public nor marked public (`invalid`, or `denied` where the level check comes first, 5.4); one already marked public keeps taking writes. |
| `epoch` | plain | current epoch: 0 to 2^31−1 for a channel; a group or DM stops at 31 and is not created past it (release 91). |
| `keys` | plain container, sealed content | `{ [epoch]: { [label]: wrap } }`. `label` is 22 random base64url characters. `wrap` is `{ epk:{x,y}, iv, ct }` to one device. Since stage 7 the salt names the epoch as well: `hush-wrap-v2|cid|epoch|handle|deviceId` (the device id empty for a wrap to the account key), so a wrap copied into another epoch opens to nothing. Wraps made before used `cid:handle[:deviceId]` and are still tried, second. A device finds its own entries by trial decryption, one key agreement per wrap. Two rules on the client guard against a server that replays old material (10.4, A3): a wrap that opens to a key the device already holds for another epoch of the chat is ignored, which is what still covers the old-format wraps; and sealed `meta` is read only when its `e` is the record's current epoch, since a stale copy would show the member list from before a removal and have the next rotation wrap for that person again (since release 93b the epoch is in `meta`'s associated data too, so a copy relabelled with another `e` opens to nothing even where one key serves two epochs). The server refuses to store `meta` under any other epoch (9.3). The admin secret's wraps (`akeys`) have no epoch and keep the old salt `cid#a:handle[:deviceId]`. |
| `akeys` | as above | `{ [label]: wrap }` of the admin secret, groups and channels only. |
| `openKeys` | plain | `{ [epoch]: base64 chat key }`, public channels only. **Who learns who is in a channel.** In any channel, public or private, only the owner and the admins may learn who the subscribers are. A subscriber is a member who is neither. The rule has two halves. The server half hands the sealed member and blocked lists (`meta`, above) and the read marks (5.4) to the owner's and the admins' connections only. The page half makes every screen and list the page builds from a channel work with no member list, so that a subscriber's page needs none (5.6, "Membership on the page"). The page half does this:

- **Counts and Channel info.** Who a channel's subscribers are is shown only to an account that is the channel's owner or an admin, by the record's owner and admins or by the level its connection holds. How many a private channel has is shown to its subscribers too, in Channel info alone (release 95), as a number and never as names. A subscriber, a link holder and a visitor to a public channel see only "Private channel" or "Public channel" in the chat header, on the chat list row of a channel with no post yet, on the join sheet and on New message's list of public channels. In Channel info a subscriber of a private channel sees the number too, as in "Private channel, 4 subscribers". Since release 93b the number is for a private channel only: it is the length of the member list the copy holds, if it holds one (a server before release 96 handed the list out). Failing that it is the record's count field `n` (table above), which the server half, live since release 96, takes on private channel records only, as a whole number from 0 to 100000. With neither, the line says only "Private channel". A public channel shows no count below admin level, whatever its record or a preview carries (release 93b; before it, Channel info would have shown a public channel's record `n`, had a server stored one, which none does today), until Phase 3, where anonymous one-per-account tokens count its subscribers without the server learning who they are. Channel info also names only the owner and the admins, taken from the owner's part (`ometa`; a public channel's plain `owner` and `admins` fields), under "Owner and admins", with no Block person or Unblock person on any row (the profile one tap away, and Settings, still block and unblock). The owner's and the admins' pages show the whole list, the count and every action as before. They also keep the record's `n` equal to the length of the list. They do it with a separate best-effort update after each change of the list and when they open the channel. A server that does not take the field refuses it, and nothing depends on it; release 93a's server was one. Rolling the server half back to release 93a's code needs every stored `n` stripped first, because that code refuses every later `update`, `set`, `chat.join`, `chat.rotate` and Make public of a record that carries one (an admin's own update of `n` is `denied`), while `chat.card` and `chat.admins` still work. A group's members still see each other and the count. One-on-one chats are unchanged.
- **People lists.** The page takes people from a chat through one rule. For a channel where this account is neither the owner nor an admin, it takes only the channel's owner and admins. "Admin" counts either the copy's owner and admins (from the owner's part) or the level the connection holds. The rule covers everything the page builds from chats: the profiles it loads at start and when it opens a chat; the "people you know" list in New message and in the people picker (New group, New channel, Add) when nothing is typed; the key pins in the vault, with their security-code toasts and the chip at the top of a chat; the presence it asks for while the chat is open; and the member list a device removal's record keeps, with the profiles its rotate stage loads.
- **What the rule leaves alone.** The owner's and the admins' pages take every member. Groups and one-on-one chats take every member, as before. Public channels are unchanged, since their shown members were already the owner, the admins and, once the account has joined, itself. The one difference is that a viewer who has not joined now also counts its own earlier reaction, vote or read mark on its own page (5.7). Under the server half, subscriber pages still pin and check the owner's and the admins' keys. Read marks, reactions and votes follow their own rule (5.7).

**Go-live order.** The page half went first, as release 94. It works with a server that still hands `meta` to every subscriber and with the server half. Then the open tabs and iPhone apps were reloaded or restarted. A page left on older code decides that it belongs to a private channel from the list, so with no list it counts the account as not subscribed: it offers no Leave or Mute, no reactions, votes or read marks, and it wraps nothing for the account's new devices. A page left on older code that may act as an owner or an admin has a second reason to reload. It seals `meta` again (Add subscribers, Unblock) from whatever copy it holds, and a copy read below admin level has no `meta`, so a subscriber just made an admin could seal a list that names only the people they add (5.6, "Writes of `meta` from a copy the page read"). So the server half went live, as release 96 on 2026-11-05, only once every open tab and every iPhone app that an owner or an admin may use had been reloaded or restarted.

Group and channel ids are `g` or `c` followed by 12 alphanumerics, as today. DM ids change: `d` followed by 22 base64url characters of `SHA-256("hush-dmid-v1|" + ECDH(a, b))` truncated. Both parties compute the same id; the server cannot; the old `dm~alice~bob` form is gone. Saved messages (a DM with yourself) use ECDH of your own key with itself and the label `hush-dmid-v1|self|`. A conversation keeps its id across a key change (release 21): once either account's keys are replaced the two keys would derive a new id, so the page keeps, in its vault, which conversation belongs to which peer (`prefs.dms`) and looks there, then in its open chats, before deriving. The DM stays one conversation with its history, and a note or a chat that names the id is recognised instead of thrown away.

**Read marks below admin level.** In a channel, reading the read marks needs admin level, by `get`, `mget`, `query`, `sub` and a watch by ids. Admin level here is the level the connection holds, so an owner or admin key held at member level (4.6) reads none until the account is secured. Below admin level the server answers as if there were none: `get` returns no document, `query` an empty list, and a `sub` or a watch gets an empty `init` that never fires and that an eviction still ends. It never answers `denied`, because a release-92 page takes a denied watch as an eviction and then stops hearing new posts. A whole mark (`set`) is still written at member level, so every subscriber still writes their own, and the owner and the admins keep their view counts. In a channel, `update` and `delete` of a read mark need admin level. Below it they are refused with `denied` ("read marks are written whole") before anything stored is read, whether or not a mark is there, so neither answer tells whether a guessed username has one. In any kind of chat, a connection with no level for the chat gets `denied` ("open this chat with its key first") and one not signed in gets `unauth`, mark or none. A stock page never sends them: `writeSeen` uses `set`, and its tidy of `reads/<handle>` is `invalid` at the path rule before any check. An owner or admin key held at member level (4.6) updates and deletes none either. Each mark sits under a tag that anyone holding the chat key can work out from a username (5.7), which is why subscribers, and in a public channel anyone who opens it with the published key, no longer read them, nor probe for them. A subscriber can still overwrite another person's mark with a whole mark of their own; the owner's and the admins' pages drop it, since its signature is not that person's. Groups and one-on-one chats are unchanged: their members read, update and delete each other's marks.

**Update and delete below the read level.** `update` and `delete` answer by what is stored: `notfound` for a missing document, `ok` for a delete with nothing there. A connection that may not read a path must therefore be refused before the server looks, or it could tell whether a document is there. Since release 96, the server half, `update` and `delete` of every path under a chat (posts, comments, acts, reads, typing, call, chunks, key-chain rows and member cards) and of `secure/<h>` (4.6) first run the check that a `get` of the path runs. Below the level that may read the path, that check's answer is the answer, whether or not a document is there, and nothing stored is read. A connection not signed in gets `unauth` ("sign in first"). One with no level for the chat gets `denied` ("open this chat with its key first"). One with a level the path does not allow gets the refusal a `get` gives there: `denied` ("this needs admin access to the chat") for a member card at member level, `denied` ("read marks are written whole") for a channel's read marks below admin level, `denied` ("calls are for one-on-one chats") for a call row outside a one-on-one chat. `secure/<h>` is refused with `denied` ("this mark is read by the server only") whoever asks. The chat record itself is left out: a connection with no level reads its preview anyway (5.5). A connection that may read the path gets the answers it got before. Before release 96 the server answered by what is stored on every one of these paths, read marks included.

Letting any member add wrap entries means any member can hand the chat key to an outsider. The chat key already leaks that way by screenshot or forwarding, and the members list is in sealed `meta`, where the clients that read it can see unexpected additions (a group's members; in a channel only the owner and the admins), so this is accepted. Clients should warn admins when the wrap count for the current epoch exceeds members times verified devices.

### 5.5 Preview read

A `get channels/<cid>` from a connection without a level for `cid` returns a trimmed record: `type`, `visibility`, `epoch`, `keys`, `akeys`, `openKeys`, and for public channels also `name`, `desc`, `photo`, `owner`, `admins`, `ts`, `last`. This is what a newly invited device needs to find its wrap, derive the chat key, derive `M_e`, and `chat.open`. The preview carries `openKeys` as stored for every kind of chat; since release 107 no new entry gets into a record that is not a public channel (5.3), and one stored before stays readable this way. `chat.invite { cid, iid }` additionally returns `{ iv, ct }` of one invite so that a link holder can decrypt the key history and show a join preview. Both are rate-limited per address bucket because chat ids, while random, may leak. A connection with member level for a channel gets the whole record except `meta`: the key wraps, the owner's part (`ometa`), the epoch, the `invites`, `ts`, `last`, the pins and the settings reach it, the sealed member and blocked lists do not (5.3). One at admin or owner level gets the whole record, and so does an owner or admin key held at member level for an unsecured account (4.6). A member of a group or a one-on-one chat gets the whole record, as before. One with no level still gets the preview.

### 5.6 Creation, joining, leaving, removal

**Create.** `chat.create { cid, d, caps: { m, a?, o? } }` from a proven connection. `cid` must be unused. `d` passes the no-names rule and schema. The server stores the hashes of the supplied keys. DMs supply `m` only; groups and channels supply all three. Because both ends of a DM can compute the same id and member key, creating a DM that already exists with a matching member hash succeeds as a no-op, so two people who start the same conversation at the same moment land in one chat.

**Invite someone to a group or channel.** The admin adds wrap entries for each of the invitee's verified devices for every epoch (in a private channel from release 92 the current epoch alone, once its key chain reaches every key the admin's device holds or can open), re-seals `meta` with the new member, and drops `{ t: "invite", cid }` into the invitee's mailbox (section 6). The invitee's device previews the chat, finds its wraps, opens the chat, and writes the chat into its vault chat list.

**Writes of `meta` from a copy the page read.** An admin's page seals `meta` again (Add subscribers, Unblock, a group's join and leave notes) only from a copy whose list it read. A copy it kept with no `meta`, an eviction preview or a copy read below admin level, is read again first. Add subscribers and Unblock refuse (`nokey`) when the list still can't be read, and join and leave notes are not acted on. So the page never seals a list that names only the people just added, or nobody. This also closes the window after an eviction, in which an Add or Unblock could do exactly that.

**Start a DM.** The initiator computes the DM id, creates the chat with `M_0`, then drops `{ t: "dm" }` to the peer and a note of its own into its own mailbox. The server has no notion of pending requests at all; the `req` field is gone.

**Message requests (as built; this paragraph was rewritten in release 108, the one before it described a design that was never built).** A person's directory entry may say `requests: true` ("Send a request first"). An initiator whose copy of that entry says so does the same as for any DM, with two differences on its own page: every note it leaves the peer while it waits for the answer is tagged `request` (until release 108 only the first was, and the plain second note of the first message, read first by a peer whose app had been closed, made the request a normal chat about every second time), and its page lets it send one text message and nothing else until the peer accepts. The first message is an ordinary sealed post in the chat. None of that is what makes a chat a request: the recipient's own page decides (section 6, "Who left a note decides what it is"), and the tag counts only where the recipient has the setting off. The recipient's page files the chat in its vault as `dms[cid] = { peer, req: "in" }`. While it stands so, the chat is not in the chat list, the Calls list or search, has no unread count, banner or read mark, cannot ring and gets no call ticket; it shows under Message requests. An open request shows its first text message and no other message; that one is drawn as any message is, with its quote box when it is a reply (the box's username and snippet are the sender's choice) and with the reactions on it: later messages, photos, polls and forwards are counted in one line ("3 more messages wait until you accept."), not drawn, and their media is not fetched; the pinned-message bar stays away; the alert comes once per chat. Accept sets `req: "ok"` and posts a sealed service message into the chat, from which the initiator's page learns the answer. Delete sets `req: "no"` and tells nobody. The recipient's page writes no note of its own for a request it has not answered, so an unanswered request goes when the server sweeps the sender's note after 30 days (section 6).

**Join by link.** `chat.join { cid, iid, proof, wraps: { [epoch]: { [label]: wrap } } }`. The server checks `sha256(proof) == invites[iid].ph` and that every label is new, then adds the wraps. A username on the chat's ban list (`chat.ban`) is refused with `banned`, both here (after the proof check, before any wrap is added) and at `chat.invite` (before the invite is looked up, so a link from before the block, which its key change revoked, says so too), so a banned person gets neither the key history nor a wrap from any link, old or new; the refusal is not counted as a wrong link. Both need an account that exists (`unauth` otherwise): a sign-up proof for an unused name costs nothing and would get round any block. Clients can't check this themselves: before joining they see only the preview (5.5), which has no `meta`. The joiner decrypted the link's key from the invite blob, derives `M_e`, opens the chat and, in a group, posts a sealed service note `{ k: "join" }` so that members see them; an admin's client adds them to sealed `meta` when it next writes it. In a channel (release 92) the link holds the current key (every key the admin's device holds, when its chain does not reach them all) and the joiner wraps only the current one, keeping any older ones on the device, older keys otherwise coming from the key chain, and the joiner writes a `join` member card instead of the note; a member whose page shows them missing from `meta` while they hold the current key writes one again (self-healing), with the link id and `m` it noted at the join (the note outlasts key changes); a joiner from release 91 noted none, so its card waits for an admin's Add (Member cards). Once the server hands `meta` to admins only (5.3), a subscriber's page reads none and can't see whether it is listed. With no list to read, it writes its card again only for a join it noted at the current epoch: once per load, at most once a week (so a card the server dropped after its 30 days comes back), and never over a pending `leave`, `dev` or `adm` card. After a key change, holding the current key means an admin listed it, so it writes none. A listed subscriber with nothing noted writes none. An unlisted joiner whose page noted no join at the current epoch, or whose note a later card replaced, waits for an Add. For public channels there is no join at all: the client derives `M_e` from `openKeys`. In a channel the joiner's wraps count against the wrap cap (5.4).

**Leave.** The leaver posts a sealed service note `{ k: "leave" }` and forgets the chat locally (in a channel, from release 92, the leaver writes a `leave` member card instead, and writes it again at each start until a new epoch shows). When an admin's client sees it, it rotates the epoch without the leaver and re-seals `meta`, marking the rotation `why: "leave"`; a "leave" note followed by a later "join" note from the same person is not acted on. Until then the leaver still technically holds a working key; this is the same as every end-to-end encrypted group messenger. A group or DM has 32 epochs (0 to 31) for its whole life, and a member can make admins' clients rotate with no admin acting (leave, get back in by link or by another member's wrap, leave again), so the server refuses a leave rotation in a group past epoch 23 (`leaveRotateMaxEpoch`, code `conflict`): epochs 24 to 31 stay for removals an admin chooses, which nothing a member does can use up. Once leave rotations are refused, the admin's client drops the leaver from `meta` with an update and no new key, and does not try again; the leaver keeps the current key until the next removal rotates it away. A channel has no epoch cap (release 91): the server takes a rotation marked `why: "leave"` in a channel at most once every 15 minutes (`leaveRotateGapMs`) and 8 times in any 24 hours (`leaveRotatesPerDay`), by its own clock, kept with the chat (`chats.lv`, 8.1), and refuses others with `ratelimit`; the admin's page waits and handles every pending leave, and every lost-device card, in the next one (from release 92 a page also marks a rotation for a `dev` card `why: "leave"`). Removals never count against the leave window (every `chat.rotate` counts with the messages, 9.4). `why` is only for groups and channels; any other value is `invalid`.

**Membership on the page.** A private channel's page counts itself a subscriber by the level its current key gives its connection (`chat.open`, 5.2), so it needs no `meta.members` for it. The server gives that level only for the current member key, and never to a blocked username (`chat.ban`). Leave, Mute, the page's own read marks, reactions and votes, the read-only composer note and `syncWraps` (the chat keys this device holds, wrapped for the account's other trusted devices) all go by that level. A copy of the channel read without `meta` shows an empty list: `showMeta` adds no one to it. So a page that holds no list makes no key change: it refuses one (`notmember`) before anything is wrapped. Groups, one-on-one chats and public channels go by the list as before.

**A record's own `id` on the page (release 108).** A page files its copy of a chat record it reads from the server under the address it asked for, whatever `id` the record carries (`chatRec` in `app/ui.js`, at the seven places that read a whole record: `capsFor`, `onChatEvicted`, `freshChan`, `ensureDmDoc`, `openNewChat`, `watchInbox`, `watchPushCall`). The record's `visibility` is taken as the server sent it, so a private channel that someone who can write the database marks public is still read as public by the page; a fix is planned for the release after 108 (`SECURITY.md`, "Public channels are readable by the server").

**Member cards (release 91).** A member of a private channel writes one sealed card with `chat.card { cid, e, iv, ct }` (member level, from an account that exists: a sign-up proof for an unused name costs nothing, so it is `unauth`; a blocked admin, who still holds the admin key, is refused with `denied`). Its plaintext (kind `join`, `leave`, `dev` or `adm`, signed by the account) is padded to 512 bytes and sealed under the chat key of epoch `e`, at most the current one, so every card is 528 bytes of ciphertext and the server can't tell the kinds apart. Someone holding an approval link asks with `chat.ask { cid, iid, proof, iv, ct }`: the proof `chat.join` takes (a wrong one, or a link that is gone, is `denied` and counted as a wrong link, 9.4), an account that exists (`unauth`), not blocked (`banned`, after the proof, not counted), the card sealed under a key from the link's secret. The server keeps one card per account per channel at `channels/<cid>/roll/<tag>`, `tag = HMAC(addr.key, "roll:" + cid + "|" + h)` (8.3), as `{ e, iv, ct, ts }` or `{ iid, iv, ct, ts }`, `ts` its own time; a newer card of either kind replaces the older one. Admins read (`get`, `query`, `sub`) and delete cards; nobody writes one with `set` or `update`. Since release 96, the server half, a connection below admin level (an admin demoted or removed who still holds tags from `chat.slots`, a subscriber, or one that is not signed in) gets one answer from `update` and from `delete` of a slot, whether or not a card sits there (5.4), so it can't test whether an account has a card. Before release 96 the server answered by what is stored. A card goes 30 days after it was written (`cardTtlMs`), with its chat, with its account (4.7), and when its account is blocked from the channel (`chat.ban`, so a join card written just before a removal can't bring the person back after it). A channel holds at most 10,000 (`cardsPerChat`): a replacement always fits; a new card past that takes the place of the oldest join request or card sealed more than one key before the current one (no admin page acts on those), and is refused with `toolarge` when there is none. The server can't see a card's kind, so an admin (or a stolen admin secret) may delete any card (since release 93b deleting an `adm` card, or blocking its author away, no longer delays the replacement of the admin secret); a page that wrote a `leave`, `dev` or `adm` card writes it again until it sees the result (a new epoch, or new `akeys`). Groups, DMs and public channels have none (`denied`). **The page's rules (release 92).** The plaintext is `{ f, k, e, i, ts, m, sg }`, the author, kind, epoch, link id or empty, the author's time and, on a link joiner's `join` card, `m`, `base64url(HKDF-SHA-256(link secret, salt "hush-join-mac-v1", info cid|iid|f))` (32 bytes; over neither the epoch nor the time, so the joiner's page, which notes it with the card, writes the same one again), with `sg` the author's signature over `hush-card-v1|cid|k|e|i|ts` (not over `m`: only the author signs a card, and only the link's secret gives an `m` for that author), padded with spaces to 512 bytes and sealed under the epoch's chat key with associated data `hush-card-v1|cid|e`. An admin's page reads the cards when it opens the channel and before every key change, and tries to list a link's joiners as opening does before any write that stops a link with no key change (Revoke alone, Remove admin, a block with no room for a key change; not before a block's key change, which leaves them out), so whoever joined through it since is listed while it still vouches for them (if the read or the write fails, the link is stopped all the same and they wait for an Add); a device removal's wipe after a failed key change lists no one (the device's new keys open no `as`, and the lost device may have let them in). A card's signature is checked against the author's current key in the directory. A `join` card counts only under the current epoch and only through its link: this admin's page opens the link's `as` with the admin secret the owner signed ("Key chain" below; the link still open, or carried across a leave) and gets the card's `m` from its secret. Its unblocked author is then written into `meta`, with no new key and no unblocking, and not by the key change of a removal or block, of a lost device or of a leaked link. A key change for leave cards alone (no `dev` card) does give the new key to the link joiners it has just listed. A link made before release 92 has no `as`: the admin's page that made it, which keeps its secret, seals one into the record (`invites.<iid>.as`, a merge update, under the admin secret the owner signed, once there is one) when it opens the channel, before it reads the cards, so from then on every admin's page vouches for its joiners and a leave carries it; a link whose secret no page kept never gets one. Any other unlisted, unblocked author of a join card (no `m`, a wrong one, a link that is gone or unknown, a link with no `as`, or no link: someone holding the current key from elsewhere, a joiner from release 91 whose page noted no link, or a joiner whose link stopped before an admin's page listed them) only shows, unticked and with its @username (a display name can be copied), under "Waiting to join" in Add subscribers (and in the chat list's notice, "The start's pass" below), for an admin to add as any Add does, and under "Waiting to join" in Revoke and remove people who joined with it, whose "Joined with this link" lists only cards whose `m` checks for that link, so for a link with no `as`, or on a device holding no admin secret the owner signed, it lists no one there, says so, and Remove and revoke is disabled there (the link can still be revoked); on the owner's own page with an unsigned admin list (a channel from before release 92 she hasn't saved yet) the sheet says the list isn't signed yet and names Edit, then Save in Channel info and the next open (release 93b); where it does list people, it says that the unticked who joined or asked since the key last changed stay under Waiting to join until it next changes, so they can still be added back, and that anyone else needs a new link (their card is then two key changes old, below). A card shows in Add subscribers and in the notice under the current epoch and the one before, so the wait lasts through one key change (a leave batch is never held back for anyone waiting): someone a key change cut off is still added as any Add is, with the current key and their note sent again (an Add sends it afresh, also to someone this device noted before, whose own page may have forgotten it), and needs no new link; a card two key changes old shows no more there (Revoke and remove people who joined with it still lists every card of the last 30 days). A join card one key back that a link still vouches for (a joiner during a leave's key change, say) only waits too: its author holds no current key. A `leave` card, and a `dev` card from a listed author whose account key has changed since this device last acted on one, count under the current or previous epoch and make one key change marked `why: "leave"` for all of them (it waits while the record's wrap tables pass 1 MB). A subscriber the list leaves out (waiting to join) writes no `dev` card when removing a device (it would replace their join card, and with it the link's code by which an admin's page lists them by itself) but their join card again, with the link and `m` noted at the join, signed by the new account key (a card signed by the old one no longer checks), so they keep waiting (an admin's page lists one whose card carries a link's code at its next open or start, as above; any other waits for an Add); the removed device reads on until the key next changes, and the removal's summary says so and that an admin may need to add them. A page with no list to read (a subscriber's, 5.3) can't tell whether it is listed, so it writes the `dev` card. A listed subscriber's card gets the key changed at an admin's next open or start. An unlisted joiner's card changes no key and lists no one by itself. Since release 104 an admin's page counts a `dev` card whose unblocked author the list doesn't name as waiting to join, like a join card no link vouches for, under the current epoch and the one before: its author shows under "Waiting to join" and in the chat list's notice, an admin adds them (no key change), and at an admin's page's next open of the channel or next start the card, now a listed author's, gets the key changed. (Before release 104 an admin's page dropped such a card: its author no longer showed under "Waiting to join", no key changed for them, and the summary's sentence was untrue for them.) The card still replaces their join card, so a link that is still open no longer lists them by itself. The lost device reads on until that key change. The removal's summary can't tell the two cases apart, and says what holds in both: "Ask an admin of these channels to open the channel: <names>. If they see you under Waiting to join, they add you, then open the channel once more. That shuts the removed device out. Until an admin has accepted your new security code, new posts there may not show for you either. If that lasts more than 30 days, ask for a new invite link." A subscriber whose `leave` card is still pending writes it again when removing a device, signed by the new account key, never a `dev` or `join` card over it (which would keep them listed, or waiting, at the next key change). An admin whose `leave` card is still pending and who removes a device in the same page session still makes the removal's key change as an admin's, with them in (wrapped to their new account key, so the removed device opens no current key), but since release 93b writes the `leave` card again under the new key, signed by the new account key, in place of the `adm` card, so the leave stands: the owner's page drops them and replaces the admin secret at its next open or start as for any admin's `leave` card, and the removal's summary says so (before 93b the `adm` card went over the `leave` card and the leave was lost until they left again). Like every key change it wraps nothing to a listed member whose new security code this page hasn't accepted, so a `dev` card's author loses the new key there along with the lost device. Such a member's page can't read `meta` without the key, so it can't tell this from a removal: once its account has changed its keys (or, with no count of days, while it hasn't read its own profile yet) it keeps a private channel's note it once held a key for, without showing the channel and without the sheet about older messages, for 30 days from the first time it finds the channel so (noted on the device; the wait ends once the channel shows or its note goes), and shows the channel again once an admin's page that hadn't accepted the code, the one that made the key among them, accepts it and hands on the current key; after those 30 days the note goes, as after a removal. A page that accepted the code before the key change hands nothing on again. So a removal or block of such an account keeps the note for those 30 days, and a code accepted only after them finds no note: a new link brings the channel back. An `adm` card makes the owner's page replace the admin secret and stop every open link; it waits while that page hasn't accepted its author's new security code, as the new secret would go to no key the page hasn't accepted. Since release 93b her page does the same by itself when a listed admin's account key version (the directory's `kv`) is above the one its roles record notes for them (`ak`, noted at each admin-secret change it makes, for the admins whose code it accepts; none noted counts as 1), once their code is accepted, so the card is only a hint; the same replacement lets the admins she lists back in at the server (a block a lost device placed on one of them is lifted). This and the drop below are made only from a list the owner's page holds signed: from an unsigned one (a channel from before release 92 she hasn't signed yet) the cards' key change goes through and these wait until she signs it ("Key chain" below). Since release 93b her page keeps an admin's `leave` card there (deleted only by the drop) and, while the record is unsigned, reads it as a member's card (within the two-epoch window, acting once), so her save finds it: her next open drops the admin before it wraps the fresh admin secret ("Key chain"), an admin another admin added back meanwhile included (before 93b the card went with the leave's key change and her save signed them in, with the new secret). The owner's page also drops from `ometa` any admin no longer in `meta` or blocked, and any admin whose own `leave` card it finds at any epoch whose key never went public (anyone may seal a card under a published key): while the list names admins it reads every epoch's cards, from a signed record (release 93b), and takes such a card even under a `meta` that names them again (their own modified app could have written it; they come back by a link, whose `join` card replaces it, not by Add: until the owner's page acts, another admin's page that acted on the card acts on it again while it is one key back, and the owner's page drops them). From release 93 the server tells an owner's or admin's page that holds the current member key which tag each author's card sits under (`chat.slots`, 7.1). Every card, those from before release 93 included, already sits under its writer's tag, because `chat.card` and `chat.ask` file it under the writing connection's username. So nothing moves, and a copy written again from another account's slot sits under that account's tag. The tag is per channel and per username, the same across key changes. The server stays the trust anchor for which slot is whose: it could answer falsely, or put an author's own older card back into that author's slot. The server half is in release 93a, and since release 93b an owner's or admin's page asks `chat.slots` once per read, with the channel's current member key, for the authors of the cards that would act, and ignores a card outside its author's slot (a page cannot tell whose slot a card sits in by itself: the `tag` above is keyed under the server's secret), so a copy written again from another account's slot counts for nothing. With no answer (a rate limit, the connection) no card acts and the run waits for the next open, never every card; a stale key (`conflict`) is asked once more with the fresh key; and a key change whose cards could not be read is not made (before 93b it went ahead with no card applied, and a copy of an admin's `leave` card written again from another member's slot had the owner's page drop that admin again each time). A card left behind (a delete that failed, or `toolarge` below) drops an admin made one again within its 30 days. An admin who left and whose modified app deletes their own card (any admin may delete one) and names them again before the owner's page acts stays an admin, as one who never left would, until the owner removes them. To drop them the owner's page starts from the list as it is by then, so an admin change made while it read the cards stands: it replaces the admin secret at its record's `rt` with the list unchanged ("Key chain"), which stops every open link, then makes a key change of its own without them, not marked `leave` (so the leave window doesn't hold it back) and applying the other cards it read as a leave batch would, and only then signs the list without them, at its record's `rt` plus one: a key the admin made before the owner's page acted, which every page took while they were still named, is used no more, where signing it again would vouch for it. A failure before the list leaves them named, so the next open does it all again; with no room for a key change (`toolarge`) it signs the current key's commit again and drops them, and a key of theirs then stays in use until the next key change. Join cards stay for the card's 30 days, so that "Revoke and remove people who joined with it" can list who joined through a link in that time; the others are deleted once applied, an admin's `leave` card only by the owner's page from a signed record (another admin's page that acts on it leaves it there, and so does her own page while her record is unsigned, release 93b). A blocked author's card is never acted on, and "Revoke and remove people who joined with it" gives the new key to no one it lists unless an admin ticks them; it never lists the owner or an admin (they hold the admin secret: only Remove admin or a block cuts them off).

**The start's pass (release 92).** Once a release-92 page's chat list is live (its socket up; after a pushed call), the page goes through the private channels its account owns or admins, one at a time with a pause after each it ran (a second after one that went through), never the one open on screen (its own open does the cards), and does for each what opening it does for an admin (Member cards: it acts on the cards, seals an `as` for a link from before release 92 it made, and on the owner's page signs a fresh admin secret's fingerprint where the signed record names none), so no channel needs opening by hand; at most once a day per channel (a stamp in the sealed store, set only when the run went through: a failure leaves it unset for the next start and moves on to the next channel, so a channel is tried at most once per start and the release-91 limits hold, a leave's rate limit leaving the cards waiting as it does at an open, while any other rate-limit answer on that key change (the connection's own, 9.4, "slow down"; a `chat.open` the connection sends first, refused or timed out) is a failure, and sets no such wait, at an open too: only the leave gap's own answer ("try again later") leaves the cards waiting; a read the server refuses, the connection holding member level only, is a failure too, and so is a card whose author's directory entry could not be read (the cards are read again at the next open or start, rather than the card passing for a deleted account's, which is skipped); a channel that failed makes the pass wait longer before the next (two seconds, then more), so a busy connection is not asked again at once, though not after one this device lacks the current key for or whose cards the server refused to it or whose current key this page refuses (`badkey`: an admin list the owner hasn't signed yet, or a planted key; release 93b, before which such a channel counted as a failure and backed off) (nothing was busy: the usual pause)), one tab at a time per account (a web lock named for the account: a tab that finds it held skips its pass, the stamps being shared through the sealed store), and it stops when the account changes or logs out or a device removal runs (the account is checked again after each step, so nothing is stamped or noted under one that came in meanwhile, and a channel whose cards were being read writes nothing more). It never signs a channel's admin list for the first time: a channel from before release 92 has no signed list, and the owner signs it once by hand ("Key chain" below). Whoever an admin's page finds waiting to join (the "Waiting to join" of Member cards) when it reads the cards, at an open or in the pass, is kept per channel in the sealed store and shown, less anyone this device's copy of the channel's list now names or blocks, and never for a public channel, in one notice at the top of the chat list, on owner and admin devices ("3 people are waiting to join your channels"), with an Add button that opens one sheet listing them by channel, unticked and with their @username; Add reads each ticked channel's cards again first, so someone listed, blocked or gone since this device last read them is not added (a block is never lifted here) and the entry is as of now, then adds the ticked still waiting exactly as Add subscribers does (the current key wrapped for them, the sealed list with them, their note sent again); the rest keep waiting (a failure part-way says to check the connection whatever its cause and, since release 93b, how many were added ("1 subscriber added. Couldn’t add the rest. Check your connection and try again."); each channel done, its people added or found no longer waiting, has its ticked boxes unticked and disabled and the button counts the rest, so a second press reads and adds only the channels not yet done; before 93b every box stayed ticked, and a second press read every ticked channel's cards again and could add again whoever a copy not yet caught up still showed waiting, with a second note), and the notice goes once no one is left as of this device's last read of each channel's cards (someone added elsewhere who then left shows until the next open or pass; Add on them alone says "No one left to add."). Nothing is added by itself: an unproved join card looks exactly like a forged one. A link no device shows is still revoked and shared again by hand; its joiners show in the notice meanwhile. What a page-only release can't do (reloading tabs left on release 90 or 91, restarting the app) stays a manual go-live step, and so does signing each channel from before release 92: the owner opens each one she owns, checks its admins, and saves the list (Edit, then Save; "Key chain" below), right after go-live and before an admin's page opens it.

**Key chain (release 91).** A channel keeps one row per epoch at `channels/<cid>/chain/<e>`: `c`, the epoch's signed key commit sealed under its own chat key, and from epoch 1 `b`, the previous chat key sealed under this one, both base64 the server can't open (`b` at most 256 characters, `c` at most 1024; epoch 0's row is exactly `{ c }`, later ones exactly `{ b, c }`, or exactly `{ c }` from the owner's connection, "The owner's repair" below). `chat.rotate` writes the new epoch's row from `back` in the same transaction; `chat.chain { cid, e, b?, c }` (admin level, channels only, not an admin who is blocked) writes or replaces the row of any epoch the channel has reached, to backfill one from before the chain or replace a bad one. From release 93, while a channel has no key-chain row at all, `chat.chain` takes only the row of its current epoch, its head: a row of an earlier epoch is refused with `conflict` (`chat.chain: a key chain starts with the current epoch's row`) and nothing is written. Once any row exists, any epoch from 0 to the current one may be written or replaced, as before. Since `chat.rotate` then needs `back` for every new epoch, a chained channel always has its head row. Members read rows with `get` or `mget` and may watch them by id; nobody writes, deletes or lists them otherwise. Once a channel has a row it is chained: `chat.rotate` without `back` is refused with `conflict` ("reload Hush"). Not `invalid`: a page from before the chain answers `conflict` as at a group's epoch 31, removing the person from the lists and keeping the server's block, where any other refusal makes it lift the block again. **Formats (release 92).** `b` is AES-GCM, under HKDF(chat key of `e`, salt `hush-back-v1`, info `cid|e`) with associated data `hush-back-v1|cid|e`, of the previous chat key. `c` is AES-GCM under the chat key of `e`, with associated data `hush-rot-v1|cid|e`, of `{ f, m, s }`: the signer, the mode (`full` until release 95), and the signer's signature over `hush-rot-v1|cid|e|H|m`, where `H` is base64url of HKDF(chat key, salt `hush-commit-v1`, info `cid|e`). Both are base64 of iv followed by the ciphertext. A page walks back lazily, one row per epoch, from the lowest key it holds; it follows `b` only from a row whose `c` opens and says `full`, and stops, marking the channel's key history as bad, when a key it gets differs from one it already holds; the post then reads "This channel's key history doesn't check out, so this post can't be opened." Before sealing a post, comment, service note or `meta` under the current epoch's key, or handing it out in a link or a wrap (reactions, votes, read marks, typing dots and member cards are not held back), a page checks that epoch's commit: it must open under that key, match `H`, verify with the signer's current key (one this device hasn't seen change; while this device runs a device removal, its own commit under the account key that removal replaced, as this device held it, also counts, so the removal can change the key), and name the owner or an admin as this device last saw them in `ometa` (kept on the device; the owner is fixed at first sight; a signed copy replaces the list only with a later `rt`, whatever its epoch, so a copy sent again from before counts for nothing, and one with the same `rt` under a later key moves only the epoch, unless the device took that `rt` under an owner key she has since replaced, or has narrowed the list already: then one under her current key, of that `rt` or an earlier one, keeps only the admins in both lists, below). Who counts is decided anew at every check and never kept; only the rest of the check is (the row read, the commit opening under the key, the signer's signature), so a corrected record, or a security code the device loads or accepts, counts from the next check with no cache to clear: the owner counts, and an admin counts only when the record was taken under the owner's signing key as the device holds it now and the device has not seen her key change without accepting it (an unsigned record counts no admin, whether from before release 92 or a copy this device could not verify; the record on the owner's own page counts as before; with no record yet, the check passes as before). Since release 93b a check that could not read the signer's keys (the profile did not load) is not kept either: it refuses once (`badkey`) and is made again from the row at the next seal, so a profile loaded later counts with no reload (before 93b that refusal was kept until a reload or an accepted code). A check that would refuse an admin only because the record was not taken under her current key first reads the channel's `ometa` once more and decides again (a signed copy that did not check out when it was read is not kept as read, so it is noted under the key the device holds by then), and one that still refuses a signer whose check it had kept makes the whole check once more from the head row, which the owner's page may have signed again meanwhile (Remove admin), before it refuses. While this device runs its own device removal, an admin on its record counts whatever key the record was taken under, so the removal can change the key. From release 92 `ometa` carries `rt`, the owner's time of sealing it (at least 2 ms later than any copy that device saw; a list its page changes by itself, Member cards, takes its record's `rt` plus one), and `rs`, the owner's signature over `hush-roles-v1|cid|e|rt|owner|admins` (admins sorted, comma-joined), followed by `|ah|at` when the copy names one; only a signed copy adds admins, an unsigned one can only remove them, and only on a device that never saw a signed one. **The date limit (release 92).** A device takes no copy whose `rt` or `at` is more than five minutes ahead of its own clock (`ROLES_SKEW`); it takes that copy, by the rules here, once its clock has caught up: by itself when that is at most another five minutes away, after loading the owner's directory entry again (so a copy under a key she has replaced meanwhile is checked against her new one), else when it next reads it. The owner's pages date copies by their clocks (at least 2 ms after the record's `rt`, which is never far ahead), so no copy, a lost owner device's included, can be dated so far ahead that her later changes never outrank it. While a copy of her list signed with her key, dated up to ten minutes ahead, waits so on a page of hers (from another device of hers whose clock is fast), that page makes no owner change dated by its own clock (Make admin, Remove admin, Edit: `nokey`, try again), which would rank below that copy and be undone everywhere once it is taken; sealing her list again (after a key change, a device removal, an `adm` card, Member cards) goes ahead; a copy dated further ahead holds no change back. **The admin secret's fingerprint (release 92).** In a channel `ometa` names `ah`, base64url of HKDF-SHA-256(admin secret, salt `hush-admin-id-v1`, info `cid`), 32 bytes, and `at`, the owner's time of naming it (later than any this device took under the owner's current key). The device keeps both with the list, from a signed copy only: a copy of a later `rt` gives them with its list (none, when it names none), and one of the record's own `rt` naming the same admins gives them when its `at` is later, so a copy sent again from before counts for nothing. It keeps with them the owner's signing key that checked the copy (`hk`), and trusts the fingerprint only while that is still her key as the device holds it (on a device that pinned her, the one it accepted), and not while the device has seen her key change without accepting it (it refuses her signed copies then too, and the secret from before her change, which a lost device of hers knew, would still match): once she has replaced it (a device removal), a signed copy that checks out under her new key and is dated at or before the record's `rt` narrows a record taken under the key she replaced, or one narrowed so already (`n`): only the admins in both lists stay, none is added (so a change of hers that only adds an admin and is dated below the record's `rt` waits for her next change), the record counts as taken under her new key from then on, and its `rt` stays; so her removal's own copy (her record's list, sealed again under her new key at its `rt`) undoes any admin a lost device of hers named in a list dated after it, whatever date that list chose; a copy at the `rt` where her page's list without an admin who left lands (Member cards) drops that admin; and the list without another admin who left, signed at that same `rt` by one of her devices that missed the first drop, brings neither back. A copy at `rt` 1 (none is written any more: a device with no signed record seals nothing again, below) narrows only a record at 1, and one dated later than the record still replaces the list whole, as before, and ends the narrowing. A device trusts no admin list it could not verify under the owner's current key as it holds it: a copy with no signature (a channel from before release 92), or one whose signature fails (signed under a key the device does not hold as hers, a lost device's say), adds nothing to a signed record and leaves an unsigned one unsigned (a first sight included); an unsigned record counts no admin for key commits, and the device never signs, seals again, hands an admin secret to, or saves such a list by itself (the owner's own change there, Edit then Save or an admin change, signs the list she sees afresh); a signed copy that failed is not remembered as read, so it is read again at the next read and taken once it verifies (her directory entry missing or stale at the first read, say). Channels from before release 92 have no signed list: the owner opens each one she owns once, checks its admins (the channel info says so), and saves the list by hand (Edit, then Save), at a fresh `rt`, and her page then makes and signs the admin secret at its next open or start; until she saves it, their members accept no admin's key change, an admin's page there makes none (`badkey` before anything is written) and backfills no chain, and her device removal replaces the admin secret there with one her own devices alone hold (release 93b; before it, none), so its admins are at member level until her save and next open; and where an admin's page made the channel's current key (on release 91), that key checks out on no release-92 page but the owner's until she saves the list (members only read, and notice nothing while channel comments stay off; an admin's page posts nothing there meanwhile, `badkey`; since release 93b the line the admin sees names a reload first and then the owner's one-time save, Channel info, then Edit, then Save), so her save is the go-live step for such a channel: right after release 92 is live, before an admin's page opens it. Since release 93b the Edit sheet names the admin list Save will sign (the admins by name, or "no admins") and points at Channel info to change them first; a device of hers served an older signed copy first (a fresh browser at first sight takes it) shows there an admin she has since demoted, whom a rename would otherwise sign in again (the list only; the secret and the server level are unchanged), so she removes him in Channel info before saving; it is a hint only, and a Save with the list as shown still signs it. The copy gives its fingerprint when it names no admin outside the record's list and either is the first under her new key, whatever its `at` (so a copy a lost device of hers signed before its removal at that `rt` counts for nothing, however far ahead its `at`), or, under the key the record already counts under, has a later `at` or names the record's own again; failing that, the record keeps its own only while the copy is under that key and leaves the list as long as it was, and otherwise names none, until her next one for the list it keeps, or a later `rt`. The owner's page names a new one only for a secret it has just made (creating the channel, an admin change, the replacements below) and otherwise signs the one its record holds, also when it seals the list again under a new key, but only one its record took under her current key (else none), and dates a new one after the record's only then; making a channel private again it names none, since the one the records hold is from before it went public and an admin dropped since may know it. A page seals a link's secret under the admin secret (`as`: Invite via link, a link from before release 92, a leave's carry, an admin change's re-seal) or opens an `as` (the invite sheet, a leave's carry, vouching for a joiner) only with the secret whose fingerprint its signed record names: it tries every wrap in `akeys` that opens, keeps only that one, and with none (no signed record, no fingerprint yet, or no wrap that matches) seals and trusts nothing: a link made then has no `as`, joins as before, stops at the next leave, and its joiners wait for an admin's Add. The admin key a page shows the server may come from any wrap that opens. Every new admin secret is written to `akeys` first and then named in a signed `ometa`, so a failure in between leaves every page refusing it. The owner's page replaces the admin secret by itself (an `adm` card, a device removal, an admin who left or was blocked, an admin's account key version risen since the secret last went out to them (release 93b), and the fresh one below) only at the `rt` of its own signed record and with its list, never a later one: an owner device the server kept a later change from brings no older list back, and a device that saw the change ignores it (or, when it took the change under an owner key she has since replaced, keeps only the admins in both lists, above). The list without an admin who left or was blocked, which it then signs by itself (Member cards), takes that `rt` plus one, which every later owner change outranks, so likewise a device that saw one ignores it (or, when it took that one under an owner key she has since replaced, keeps only the admins in both lists, above). Right after it makes a channel private again, and when it opens a channel whose signed record names no admin secret (one from before release 92 whose list the owner has saved once; one made private again whose fresh secret didn't land), never on an unsigned record, or names one other than the last one this device made itself while a wrap of that one is still in `akeys` (its list didn't land), it makes a fresh one so, wrapped to the owner and the admins whose security code it has accepted and, since release 93b, whose `leave` card isn't waiting (it reads the cards first when the list names admins; an admin whose card waits is dropped by that same open right after, so no admin secret it writes reaches them), before it seals any `as`. Any other mismatch it leaves (a wrap swapped in; a change from another device, or from a page from before release 92, that this device hasn't seen; a device added since): every page then refuses the secret until the owner's next admin change from a release-92 page. After a key change the owner's page seals `ometa` again under the new key with the `rt` of its own signed record, and only while that record is still the one it read the copy against; with a record that isn't signed (a channel from before release 92, a new device, a fresh browser) it seals nothing again. Ordering by `rt` first is the smallest rule that covers both an owner device the server kept a later change from (one made on the owner's other device, say), which seals the list it last saw again under a later key but with that list's older `rt`, so a device that saw the change keeps it (unless the key she signs with was replaced in between, a device removal: then it keeps only the admins in both lists, above), and the owner's own change sealed under the key its page started from while a key change landed and its page sealed the old list again under the new key: later by `rt`, it still counts everywhere, the owner's own record included. On a device with a record, signed or not (an unsigned one only ever loses admins), the owner and admins a page shows and writes are the record's, never a copy's. The owner's page seals `ometa` again only when the copy names the record's owner and admins and is not older than the record (by epoch, or by `rt`; a copy with no `rs` by epoch alone), and any owner write built from an older copy (Make admin or Remove admin, a removal of an admin, Edit, Make public, its leave run's admin step) refuses with `nokey` instead of signing it again. The owner's page writes `ometa` one at a time per channel and puts each into its copy of the channel and its own record at once, so a server that keeps the echo from it can't have it seal an older copy again. A page that isn't the owner's changes no private channel's key (`badkey`) when its record is unsigned, or signed and names its account no admin: every member would refuse that commit. A device that never saw the channel's chain accepts a missing row (channels from before) unless the row before it exists; once it has seen the chain, it refuses one. Until it has, that is so on any channel, not only one from before release 92, since a server can answer it that a channel has no rows. Every rotation writes its row; the first owner page, or admin page whose record is signed, to open a channel with no rows backfills rows for every epoch it holds both keys for, head first (not on a device that has seen the channel's rows or made one: there the server may be hiding them; and only while the record, read again before the first row is written, is still at the epoch the page's copy shows, since rows below a newer head would leave that head missing; and a key change that lands between that read and the first row, one from a release-90 page with no `back`, can no longer leave the head missing either: from release 93 the server refuses that row with `conflict`, the channel stays unchained, members keep sealing under the new key, and the backfill runs again at the next open, head first); a chained channel's head is never written outside a rotation; a new channel writes row 0 at creation; and the owner re-signs the current commit, as the record holds it then, with the key before from its own store (else the row's own `b`; with none for a repair row, release 93b), before dropping an admin, and signs it again if the key changed before the admin key was replaced (Remove admin; an admin its page drops by itself gets a key change instead, Member cards, and the commit is signed again only when there is no room for one). The backfill trusts no key the server can supply: it puts in `b` only a key the device holds itself (stored, in a wrap of its own, or walked), never one from `openKeys` alone, and only one that matches the `b` of the row above; it writes a missing row only below every row the channel has, replaces a present one (never the head, nor one not marked `full`, and, from release 93b, never a row with no `b` above epoch 0, the owner's repair, where the walk stops) only when the row below opens under the key held and its commit checks out as the head's must, by the owner or an admin this device has on record (never at first sight), or, for row 0, which holds no key, under the key the chain gave, and writes nothing at or below an epoch in `openKeys` (a channel made public and then private again: anyone may seal a row under a published key), so links from such a channel carry every key. In a private channel a key the device holds for an epoch, stored or in a wrap of its own, wins over `openKeys`, which count only for an epoch it holds none for. **The epoch-rollback guard (release 93b).** From release 93b a device keeps, per private channel, the highest epoch whose key change it checked (the commit's signer the owner or an admin on its record) or made or took from a link, in its roles record (`hi`, 12.2), and seals nothing, hands nothing on and changes no key from a record below it (`rollback`, code `conflict`; the owner's part, which sits at any epoch up to the current one, is still written): a server serving an older record, or a database restored from before that key change, would otherwise have it seal under a key someone removed since still holds and have the owner's next key change wrap for them again at an epoch already used. The mark never lowers, and a first sight raises none (a key planted then could not lock the channel afterwards). A copy merely behind is read again first (a post) or meets the refusal as a conflict and is redone from a fresh record (a block, Revoke and remove people who joined with it, a device removal); the message names a reload. Groups and one-on-one chats keep no mark (owner decision D7; A3): a malicious server can plant a key there anyway, so the guard would only cost an honest restore (8.6).

**The owner's repair (release 93).** A key-chain row above epoch 0 may carry no `b`, a fresh key chained to no key before it, only when the connection that writes it is at owner level for the channel, meaning it opened the channel with its owner key or created it. The rule covers both writers, `chat.rotate`'s `back` and `chat.chain`, and any epoch from 1 to the current one, so she may also re-sign a repaired head, or replace a lower row, without `b`. Nothing the client sends sets the level (a `level` field in the frame is ignored). The owner's own account on a connection that opened with the admin key is at admin level, and an owner whose account isn't secured opens at member level and can neither rotate nor chain. Below owner level a row with no `b` above epoch 0 is still `invalid`, with the message `chain row: field "b" is required`. At every level, epoch 0 with a `b` is `invalid` (`chain row: field "b" is not allowed`), and so is a `b` that is null, empty, longer than 256 characters or not base64 (`chain row: bad "b"`). The sizes are unchanged, and the head rule above holds for her rows too. The row is for a channel whose current key every release-92 page refuses (SECURITY.md, "fails closed"), which only the owner can repair, with a new key she signs. The server half is in release 93a. No page writes such a row before release 93b. Since 93b Channel info offers the owner of a private channel whose current key her device refuses (`badkey`) a Fix channel action (tagged "Needs fixing"): the sheet names who gets the fresh key as her device holds the list (her signed admins, ticked and not for unticking; the subscribers, ticked, for her to check, since whoever made the refused key may have written the list sealed under it), says once that people who later join through the key chain see no posts from before the repair while invite links still carry every key, and on confirm the page makes a key change at the next epoch whose row is her signed commit alone (no `b`), wrapped to that list (her signed admins and the people she left ticked: her confirmation wins over the blocked list sealed under the refused key, so anyone she keeps is taken off it and, once the admin secret is replaced, the server's block on them is lifted, best effort, as Add subscribers lifts it for the people it adds; a block on anyone the sheet does not show stays, whoever placed it), carrying no link (every open link stops), and replaces the admin secret in the same run (the list signed again naming it); it works only from a signed record (D1) and only while the key is refused. Whoever made the refused key may have written the blocked list sealed under it too (a lost admin device's page blocking the real admin, say), so for the people the sheet shows the owner's ticks outrank it. The sheet shows her signed admins and the members as her device holds them, and Channel info's Block takes a subscriber off the member list as it blocks them, so a subscriber blocked that way is not in the sheet, is not lifted, and stays blocked in the sealed list and at the server, whoever placed the block: after a repair the owner still checks Blocked from this channel and unblocks (and adds back) anyone wrongly there. A server block the page could not lift (the connection lost right after the repair) shows nowhere, since the sealed list no longer names the person as blocked; Block from this channel, then Unblock, then Add subscribers puts it right. Release-92 pages already take one, with no change to their code. The commit check reads only `c`, so the repaired key checks out once her signed commit does. The walk follows only `b`, so it stops at the repair row without marking the history bad, and waits 30 seconds, as at a gap. The backfill writes nothing at or below a repair row (a row with no `b` above epoch 0 ends its walk, whatever the row below would pass) and reports the chain unfinished, so a link, Add or Resend hands on every key its maker holds; the owner re-signs a repaired head without `b` (Remove admin), and a page's backfill run from before the repair counts no more. The cost is that someone who holds only keys from the repair on (a wrap after it, or the chain) reads nothing from before the repair. A link still carries every key its maker holds, and members keep the keys they had.

**Links across a key change (release 91).** A rotation wipes every invite as before, except those in `chat.rotate`'s `invites` (channels only): each must be a link the record holds, under its id with the same `ph`; its `iv`, `ct`, `ts` and `as` are the ones given (`invalid` otherwise, and nothing changes). The server can't tell an open link from an approval link, so which links carry over is the page's rule (decision 3 of the history plan: over leaves and steps, wiped otherwise; approval links over every rotation). The page's rule (release 92): a rotation marked `leave` with no `dev` card and no admin among the leavers carries every link whose `as` this admin opens with the admin secret the owner signed ("Key chain" above), re-sealed for the new key; every other rotation, including Revoke and remove people who joined with it, carries none. Adding admins re-seals every `as` under the new admin secret; dropping an admin or acting on an `adm` card stops every open link instead (whoever held the admin secret knows the link secrets). After reading a link the page clears it from the address bar.

**Pruning (release 91).** `chat.rotate` with `prune: true` (channels only) keeps only the new epoch's wraps in `keys`, and drops the wrap counts below it. It needs `back` and a chain row for every epoch from 0 to the current one (`invalid` otherwise; the rows are counted, not checked for `b`), so a device that holds none of the older keys can still walk back to epoch 0 and check each commit, as long as no owner's repair row (above) sits in the chain. Pruning above a repair row would drop wrap tables that the chain no longer reaches. No page sends `prune` yet.

**Remove or ban.** The admin rotates: new chat key, wraps for the remaining members' devices, new `M_{e+1}`, `meta` re-sealed with the member removed and optionally added to `banned`. The removed member's connections are evicted at once and their old key no longer opens anything. A ban is also kept by the server, since another admin's client could otherwise write the person back into `meta` and wrap a later key for them: before rotating, the admin's client sends `chat.ban { cid, h, on: true }` (admin level; groups and channels, not DMs), and the server keeps a tag of the chat and the username keyed under its own secret (`HMAC(addr.key, "ban:" + cid + "|" + h)`, 8.3), at most 1000 per chat (`bansPerChat`) from admins and as many again from the owner (the tags can't be listed, so junk a rogue admin added can't be found, and must not stop the owner). From then on `chat.open` refuses that username's member key with `denied`, even when a key was wrapped for them again (the member key itself is shared, so another account holding a leaked current key still opens the chat, 5.4) (the right key, so it is not counted against the wrong-key allowance, 9.4), and their connections that hold the chat at member level lose it at once; `chat.join` and `chat.invite` refuse them too (Join by link). Owner and admin keys are never refused by a ban: a blocked admin keeps the admin key until the owner replaces it, but may not lift any block while blocked (only the owner may then), and the owner's client replaces the admin key before blocking an admin. A client whose key change fails after blocking lifts the block again, so the server and `meta` agree, except when the key's commit does not check out (`badkey`): the block then stays on the server, and `meta` and the key are unchanged (unless the owner's replacement of the admin key, the first step of blocking an admin, is what fails: then no block was placed, and the page says so); one that lost the race to another admin's rotation does the removal once more from the fresh record. In a channel (release 92) only `toolarge` keeps the lists-only fallback (the block stays, and the same write stops every open link, `invites: null`); after a second `conflict` the removal fails and the block is lifted. Every open link stops working, and the page offers a new one. At epoch 31 of a group, with no key change left, a block goes into `meta` without a new key, and the server's block is then what keeps the person out. A blocked admin may not rotate either (release 91): a key change they made could wrap the new key for themselves. A public channel has no blocks: `chat.ban` refuses to make one, and the change to public deletes the chat's blocks. A group made before the server kept blocks has them handed over, once per load until it has an `ometa`, by any admin's or the owner's client (before that `ometa` is written). Unblocking (`on: false`), from the blocked list or by adding the person back as a member, lets the member key in again; deleting the chat deletes its bans. Clients also refuse to re-add: an admin's client never wraps a new key for anyone on `banned`, and writes a "join" note's author into `meta` only when they are not on `banned` the note was sealed under the chat's current epoch (an older one may predate the removal), and no later "leave" note from them follows it (a copy of an old note keeps its sealed time, so it sorts back into place). A join note that came just before a rotation no admin's client had acted on is therefore not written in; "Add members" brings that person in. The page blocks only in private groups and channels; public channels are moderated by deleting posts.

**Appoint or demote an admin.** Owner writes `chat.admins { cid, akeys, cap }` with wraps of a fresh admin secret for the current admins' devices and the new admin hash, then re-seals the admin list in `ometa` (5.3; in a channel from release 92 an `ometa` naming the new secret's fingerprint, with the list as it stands then, follows the `akeys` at once) and drops `{ t: "admin", cid }` to a newly appointed admin so their client knows to scan `akeys`. The page demotes in that order, so a failure in between still names the admin in `ometa` and the owner's next try finds them again; it appoints the other way round (`ometa` first), so the admin secret never reaches someone `ometa` doesn't name. In a private channel, an admin change made from a page from before release 92 writes an unsigned `ometa` that release-92 pages don't adopt ("Key chain" above: the record keeps the signed list, and the owner's page seals again only a copy that names that list); someone appointed that way holds the admin secret but is no admin to a release-92 page whose record is signed, and changes no key from one; someone removed that way stays an admin to every release-92 page whose record is signed (a key change of theirs still checks out there, though the server refuses it); and the owner makes the change again from a release-92 page. Its new admin secret has no signed fingerprint, so release-92 pages seal and trust no `as` under it until the owner's next admin change from a release-92 page ("Key chain" above). A release-92 page whose record is unsigned (their own, say, if it first read the channel's settings after that change) counts them as no admin either ("Key chain" above): their page makes no key change there (`badkey`), so no page is left refusing the current key. So every tab left on release 90 or 91 is reloaded before go-live, and no admin is appointed from one.

**Ownership transfer** is not supported in this version. `chat.owner` (5.1, release 21) only lets the owner replace their own key after their account keys changed; the owner stays the same person.

### 5.7 Posts, edits and deletes without identity

Only sealed posts exist in the new server; the named format (`from`, `iv`, `ct`, `sig` in the clear) and the `req` slot are rejected. A post is:

```
{ sl: 1, ts, e, n, d, exp?, oh, on: 0 }           sealed message
{ sv: 1, ts, e, n, d }                             sealed service note
```

- `n` is the base64 12-byte nonce, `d` the base64 ciphertext of `{ f, i, c, s }` (sender, inner nonce, inner ciphertext, sender signature) under the chat key with AAD `hush-env-v1|cid|pid`, as today.
- `oh` is the hex SHA-256 of a one-time token only the author can compute, `on` its counter. To update or delete, the author sends `ot` with `sha256(ot) == oh`; the server verifies, strips `ot`, and requires the new `oh`/`on`. Updates may only touch `ts, e, n, d, exp, oh, on, edited, del`. This is today's `ownsSealed` rule unchanged. The token is derived (HKDF) from the account's private secret `own` (5.1); accounts from before stage 7 have none and keep deriving it from the signing key, so their older messages stay editable.
- Server-generated ids (`add`) are 12 alphanumerics. Client-chosen ids must match the same pattern.
- `ts` is client-set milliseconds and must lie within 30 days in the past and 400 days in the future, because scheduled messages exist.
- `e` is an integer 0 to 2^31−1. In a channel (release 91) it is the current epoch for a new post, comment or service note and for every act (where it is then required); an update keeps the stored `e` or moves to the current one; `conflict` otherwise, so the page seals again and sends again. Groups and DMs check only the range.
- The server deletes posts whose `exp` has passed on its own, every minute. From release 91 a post that expires or is deleted takes its reactions and votes (`acts/<pid>~…`) and its comments with it, in one transaction, in every kind of chat; and the sweep removes a chat's `last` (5.3), a copy of its latest message, once the copy's own `exp` has passed, whatever happened to the message (the record is announced with `last: null`).
- In a chat with a message timer (`ttl`, 5.3) a sealed message must carry `exp` of at most `max(ts, server time) + ttl` seconds, with a minute's allowance for clocks; an update may keep the stored `ts` and `exp` or satisfy the same rule (`invalid` otherwise). The page sets `ts + ttl` for a message and the server's time + `ttl` for its hidden wake tickets, which are dated before the chat's last message so nothing moves. `exp` is under the sender's signature, so the server never rewrites it; it refuses. Service notes carry no `exp`. In a DM either member may change `ttl` (5.3), so there the bound holds against a stock page, and against a modified peer only between timer changes it could make itself; in a group or channel the timer is the owner's, so the bound holds in full. A page keeps the timer it last saw per chat (12.2) and, when the record's timer has moved with no service note of the new value, shows a local line in the chat ("Message timer changed to … by the other side"); a message whose `exp` exceeds the chat's timer by more than a minute shows its real lifetime beside the timer mark.

Reactions, read marks and typing dots keep their current tagged form: id `<pid>~<tag>~<kind>` or `<e>~<tag>`, body `{ post, kind, e, iv, ct, ts, sg }` or `{ ts, sg }`. Clients verify `sg`; the server does not.

A channel's read marks are read back by its owner and admins only (5.4). A page names read marks, reactions and poll votes by one of two rules. In a channel where this account is neither the owner nor an admin, it names, counts and checks the signatures of only those of the owner, the admins and itself, whatever list its copy carries, so it loads no other subscriber's profile for them. In a group, a one-on-one chat or a channel it owns or runs, it names them over the list it holds or, with none, over the owner, the admins and itself. Before release 98, a subscriber's page also counted a channel's reactions and poll results over only those; since then it counts a channel's as the next paragraph says. No view count shows at all since release 96, whose server hands that page no read marks. The page still shows, and can take back, its own reaction and vote. A viewer of a public channel who has not joined now also counts its own earlier reaction, vote or read mark on its own page; nobody else's naming changes. Anyone holding the chat key can work out the tag of a guessed username, so a subscriber, and in a public channel anyone, can still match a reaction or a vote to it.

**Hidden reactions and votes (since releases 97 and 98, 2026-11-09).** In every channel, public or private, nobody, the owner and admins included, can see who reacted or voted, or what any named person picked. Everyone who can read the channel counts the same rows the same way, by emoji and by poll option, and your own app shows your own choice. A row goes through `chat.act` and sits at `acts/<post>~<slot>~<kind>`, where the slot is a keyed hash with the server's address key over the chat, post, kind and username, cut to 22 characters. It holds `post`, `kind`, `e`, `iv`, `ct` and the mark `an: 1`, with no name, tag, signature or time. The choice is padded to 64 bytes and sealed under the chat key at `e` with associated data `hush-act-v3|cid|post|kind`. The same account on the same post and kind writes over its row. `set`, `update` and `delete` of acts in a channel are refused at every level, with one answer whether or not a document is there. `chat.mine` tells an account which rows are its own, on every device, in the reply to the connection that asks and nowhere else. A page draws a channel's counts as soon as it has opened the rows, then asks `chat.mine`; until that answers, it marks as yours only the rows it already knew, and a poll where it does not know your vote yet shows its buttons and its total, with no results. Rows from before this change stay stored, read as none for everyone, are never answered with `denied`, and go with their post. A row stays counted after its author leaves, is blocked or deletes their account. The server itself can still tie a row to an account, because it computes the slot (SECURITY.md). The paragraph above still holds for read marks, and for reactions and votes in groups and one-on-one chats. Groups and one-on-one chats do not change.

## 6. Mailboxes

A mailbox replaces the old `inbox/<handle>/c/<cid>` list, which was a plain map of who is in what.

Each person's mailbox is `inbox/<h>/c/`: sealed notes at random ids, each an ECDH wrap to the owner's account key, readable and deletable only by `h`, never edited. A note says which chat exists, from whom, of what type. The server sees a recipient, a blob of one fixed size, and the hour. Stage 4 built the notes and their live delivery through the ordinary `sub`. Stage 5, as built, changed one thing: who writes them. A note to anyone else is posted to `POST /drop` with no session, so no connection of the sender's ever links sender to recipient. A connection may still write notes into its own box (the chat list keeps a note per chat for its owner); writing into anyone else's box over the socket is refused. The pull-and-ack ops once planned here were never needed: the live subscription delivers, the owner deletes.

**Drop.** `POST /drop` with JSON `{ to, blob, pow? }`. No cookies, no session, no proof. A request whose `Origin` header is present and not allowed (10.4, A4) is refused first with 403 `denied`, before anything is read or counted, and a request with no `Origin` goes on. The server charges the sender's address bucket for every other attempt first, so probing names costs the same as dropping. It then requires `to` to be a handle with a directory entry and `blob` to be a sealed note of exactly the padded size, stores `{ epk, iv, ct, ts }` at `inbox/<to>/c/<random id>` with `ts` the receipt hour, and the recipient's open watch, if any, is pushed the note at once. Replies: 200 `{ ok, id }`; 400 `invalid`; 403 `denied` (release 93: another site's page, with no CORS headers); 404 `notfound`; 413 `toolarge`; 429 `ratelimit`; 429 `pow` with `{ bits, hour }` when proof of work is needed.

**Blob.** `{ epk:{x,y}, iv, ct }`, an ECDH wrap to the recipient's account ECDH key with salt `hush-inbox-v1:<to>`, the same construction as `wrapTo` in the client. The plaintext is JSON padded with trailing spaces to exactly 1024 bytes, so `ct` is always 1040 bytes. One size class; nothing needs more. The plaintext:

```
{ t:"invite"|"dm"|"request", cid, from, to, ts, type?, peer?, sg? }
```

The first message of a request is not in the note: it is an ordinary sealed post in the chat, already end-to-end encrypted.

**What the recipient checks.** A note is trusted only if its claims hold up, and a note that fails is deleted: it names this box as `to`; a one-on-one note names the chat id the recipient computes from the sender's account key (5.3), so nobody can plant a chat under someone else's name without a signature at all; an invite carries `sg`, the sender's account signature over `hush-drop-v1|invite|from|to|cid|ts`, verified against the sender's directory entry (invites from before notes were signed carry none and are let through: the chat key is the real gate on whether anything can be read); and the sender is not on the recipient's block list, which lives in the vault. Verifying a signed note from a stranger means fetching their profile right then, which a live observer can correlate with the drop; this is adversary A2's existing view and is accepted.

**Who left a note decides what it is (release 108).** After those checks the chat watch judges every note that is not the recipient's own, at every start and on every change of the mailbox. "Own" is the stored mark `own`, which the server sets only on a note written over the owner's signed-in connection; a name inside a note proves nothing here.

- *One-on-one notes.* When the recipient's directory entry says `requests: true`, a one-on-one note from someone else is a request whatever its tag says, unless one of the recipient's own notes names the chat, or the vault already knows the chat, or the vault holds an accepted or self-started one-on-one chat with that person under another address (an older address after a key change; a request not yet answered, or deleted, does not count). The page reads its own directory entry from the server again before it judges such a note. While it holds no copy of that entry at all, or the entry says `requests: true` and the vault is not read, the note waits and nothing is filed, shown or deleted; when the fresh read fails and the page already holds an older copy of the entry, the older copy decides. With the setting off the tag decides, as before release 108.
- *Invitations.* An invitation that is not the recipient's own and carries no signature is dropped under any name, as a forged note is (deleted once a week old), and so is one that names a one-on-one address. A signed one goes in as before when the chat is one this page already shows or a public channel the vault says the recipient joined. A stored key does not count (any read of the record stores the inviter's wrap), so an add after leaving or removal is held like any other once no page of the recipient shows the chat and no own note names it: a page that was not connected when the recipient left on another device still shows the chat and lets the note in (`adopt` may then write an own note), and an own note that no page has deleted after a removal keeps the chat. Every other signed invitation is held, whoever the inviter is, a person the recipient has an accepted or self-started one-on-one chat with too (with the setting off one one-on-one note makes anyone such a person): the page does not open or watch the chat, writes no note and no member card, and sends the server nothing that names it unless the recipient opens a link to the chat (`handleJoin` reads the record and opens the chat at member level before the Join sheet). It shows under Message requests as "@name invited you to a group" or "… to a channel" (the inviter's username, which the signature proved, and the kind from the address letter; no name the inviter chose), with Join (the recipient's own note for the chat, as every join writes; the chat then shows as before), Delete (the note goes) and Block (the person is blocked and the note goes). The inviter is told nothing. A held invitation whose inviter is blocked later is dropped. An invitation someone else left for a chat the recipient's own note already names (with a signature or without, and also one that names a one-on-one address) never takes that note's place: it is not shown and not held. It is deleted once one of the recipient's own notes for the chat carries the same hour or a later one. While every own note is older, the page writes the recipient's own note again as it was, at most once per chat for the newest hour of such invitations however many there are (one in a later hour than those already answered writes once more; a chat watch that has ended writes none), and passes the invitation over; the note written again carries the page's hour, so the invitation is deleted at a later pass (where the page's clock is in an earlier hour than the server's it stays, not shown, at most until the server sweeps it after 30 days). A page from before release 108 keeps the newest note for a chat and deletes the other, so deleting the newer one at once would leave the chat with no note. A held invitation goes when the server sweeps the note after 30 days.

What this does not do. The server still takes the member list and the key wrap an inviter writes (5.6), so the recipient's username can stand in a group's list, where its members see it, before any Join. Removing a device (14, item 15) writes every readable note again as the recipient's own, which joins every held invitation and files a one-on-one note not yet judged as a normal chat. A page from before release 108 that is still open on one of the recipient's devices judges by the tag and writes its verdict into the shared vault, where the new page finds the chat already known. A changed sender can still store messages in a request chat; the recipient is shown none of them but the first text before Accept, though the page downloads the sealed records (not their media) to count them.

**Proof of work.** Asked for only when the recipient has "only my contacts" on (`requests: true` in their profile) or when their mailbox has taken more than half its hourly allowance. The puzzle is stateless: `sha256("hush-pow-v1|to|hour|nonce")` must start with `bits` zero bits (16 by default, about a second in a browser). The server verifies with one hash and remembers used `to|nonce` pairs in memory for the hour, so a solution is good once. The sender's page solves it on a 429 `pow` reply and posts again.

**Retention.** A mailbox holds at most 500 notes; past that the oldest give way, other people's notes before the owner's own, and the owner's watch is told, so nobody who was away for a week is locked out of new invitations. Notes from other people older than 30 days are swept hourly. A note the owner wrote to themselves (`own: 1`; only they can write in their mailbox, everyone else goes through `POST /drop`) is never swept: those notes are their chat list (release 17). The page replaces a note someone else left with its own once the chat shows, and of two notes for one chat keeps the newest.

What the server can see: that mailbox `bob` received a 1 KB note at hour H. It cannot see from whom, about which chat, or of what type. A live observer at the server can still see which network address made the POST.

### 7.2 Server to client

```
{ i, ok: true, ...result }
{ i, ok: false, e: "<code>", m: "<human message>" }
{ s, t: "init", docs: [{ id, d }] }           first result of a subscription
{ s, t: "set",  id, d }                        a document now matches
{ s, t: "del",  id }                           a document was removed or no longer matches
{ t: "evict", cid }                            your level for this chat was revoked
{ t: "mail" }                                  something arrived in your mailbox
{ t: "bye", reason }                           server is closing the connection
```

Error codes: `unauth`, `denied`, `notfound`, `exists`, `invalid`, `toolarge`, `ratelimit` (from the frame allowances of 9.4 it carries `retry`, in milliseconds, since release 100), `conflict`, `version`, `pow` (a drop, section 6, or a sign-up, 9.4, that must bring proof of work first; the reply carries the puzzle), `full` (media refused because the chat's allowance or the server's disk is used up, 7.7), `banned` (`chat.invite` or `chat.join` from someone on the chat's ban list, 5.6), `gone` (`prove` as, or a sign-up of, a username whose account was deleted, 4.7), and `internal` for an unexpected server failure. A frame that cannot be parsed at all gets an error reply without `i`; five such frames close the connection.

Close codes. Before it closes a connection the server pushes `bye` with the reason, then closes the socket: with code 1000, or with 4401 (release 21) when the connection's proof no longer stands: `keys changed` when the account's keys were replaced over another connection and this one was proven against the old ones, `username taken` when a sign-up proof's name was created over another connection (4.2). A page closed with 4401 can't get back in with the keys it holds: its next proof is refused, and it signs the account out on that device (12, item 9). With 4410 `account deleted` when the account was deleted (4.7): every connection of the account is closed so, the deleting one after its reply; any next proof is refused with `gone`.

### 7.3 Write semantics

- `set` replaces the whole document.
- `update` applies RFC 7396 JSON merge patch: nested objects merge, arrays replace, a `null` value removes the key. This is a deliberate difference from Firestore, which stored `null`. Every place the client sets `null` (`name`, `photo`, `meta`, `last`, retired device entries, retired wrap fields) only ever tests the field for truthiness afterwards, so removal is compatible. SQLite's `json_patch` implements exactly this.
- `add` generates the id.
- A write is acknowledged only after it is committed. The adapter uses the acknowledgement to flip a post from "pending" to "sent". Pushes caused by the write go out while it is applied, so a connection that both writes and subscribes receives the `set` push before its own `ok`.
- Maximum nesting depth 6. Keys must match `^[A-Za-z0-9_.~-]{1,64}$`. Top-level keys may not start with `_` (the old adapter's `_uid`/`_by` stamps); nested keys may, because wrap labels and member tags (9.1) are random base64url and one in 64 begins with `_`. `__proto__` is refused at every level.

### 7.4 Queries and subscriptions

`w` is a list of `[field, op, value]` with `op` in `==`, `<`, `<=`, `>`, `>=`. `o` is `[field, "asc"|"desc"]`. `l` is required, at most 1000, at most 10 on `search`. Two range conditions on the same string field express the prefix search the client already does.

Queries are allowed only on: `channels` (only `visibility == public`), `channels/<cid>/posts`, `acts`, `reads`, `typing`, `comments`, `channels/<cid>/media/<mid>/chunks`, `channels/<cid>/roll` (admins, release 91), and `search`. Everything else is fetched by exact path. The `array-contains` operator is gone with the members list. The public listing (`channels`, `visibility == public`) is a query only: a `sub` with `w` on `channels` is denied at every level, where it used to stream the id and time of every chat record change on the server. A `sub` with `ids` still watches chat records. Since release 110 the listing takes that one condition and no `o`, and anything else is denied: it comes in id order, read through its own index, so the server reads no other chat record for it and sorts none.

A subscription sends `init`, then one `set` or `del` per changed document that matches `w`. Ordering and `l` are applied by the server for `init` and by the client thereafter. `sub` with `ids` watches a set of documents in one collection and is how the chat list watches its chats. Limits: 600 subscriptions per connection, 1000 documents per subscription. A pushed `set` of a chat record carries the record as the watcher's connection may read it when the change goes out, by the level it holds then and not the one it held when it subscribed, so a key opened since, higher or lower, counts from the next change on. A channel's record loses `meta` for a watcher below admin level (5.3). A watch below admin level is never refused for it (never `denied`), because a page takes a denied watch as an eviction. No other push is read again at that moment: a watch of any other document or collection keeps what it was allowed when it was made, until an eviction ends it (5.2). So a watch of a channel's read marks made below admin level starts empty and never fires (5.4), while one made at admin level goes on hearing them if the same connection later opens the chat again at member level. That connection held admin level when it subscribed.

### 7.5 Connection life cycle

`hello` within 10 seconds of connecting or the socket is closed. `ping` every 25 seconds from the client; a connection silent for 90 seconds is closed. On reconnect the client repeats `hello`, `prove`, `chat.open` for each chat it holds keys for, and every `sub`. Protocol version mismatch returns `version` and the app shows "please reload". A connection proven for an account whose key version rose on another connection is closed with 4401 `keys changed` (4.2, 7.2): its keys are stale, and a reconnect with them is refused.

### 7.6 Search

`search/<h>` holds `{ h, n, n2 }` exactly as today. Prefix queries on `h`, `n`, `n2` with `l <= 10`. The index is opt-in through `findable`, which is why it may be plaintext: a person is listed, and so found by display name or part of a username, only when their directory entry has `findable: true`, which they set in Settings > Privacy. A missing `findable` means not listed (release 24; before that the page treated it as listed). Typing someone's exact username always finds them, as starting a chat needs: `directory/<h>` is readable by exact path either way, so hiding it in the page would only pretend. At startup the server deletes every `search` entry whose owner's directory entry lacks `findable: true`, so accounts from before release 24 are unlisted until they turn search on.

### 7.7 Media over HTTP (stage 6)

Photos, GIFs, videos, voice messages and any other file are media. Their bytes travel over plain HTTP requests as raw ciphertext, not as base64 inside socket frames.

**Encryption (client).** Every attachment gets a fresh random 256-bit key of its own. The file is cut into pieces of `pieceBytes` (1 MiB) of plaintext; piece `i` of `n` is AES-GCM under the file key with a random 12-byte iv and the associated data `hush-media-v2|i|n`, so a piece cannot be moved to another place, the file cannot be cut short, and pieces of different files cannot be mixed. On the wire and at rest a piece is its iv followed by the ciphertext and tag. Video is sent exactly as recorded, never re-encoded or downscaled; photos over 4096 pixels are scaled down to stay sendable.

**The sealed descriptor.** The message that shows an attachment carries, inside its sealed body, `{ id, v: 2, k, kind, mime, size, chunks, hash, w, h, dur, wave?, name? }`: the media id, the file key `k` (base64), the kind (`image`, `gif`, `video`, `voice`, `file`), the type, the size and piece count, and `hash`, which is SHA-256 over the concatenated SHA-256 of each plaintext piece in order. The reader checks `hash` before showing anything; it is covered by the message signature. There is no preview image: a client downloads and decrypts a photo or video by itself as soon as its message is on screen or within about a screen of it (videos only up to `videoAutoBytes`; larger ones on tap), shows a plain neutral box of the right shape until then, and shows the media at full quality once checked. Media further away waits until it is scrolled near.

**Albums.** One message may carry up to `filesPerMessage` attachments in its `media` list, in the order they were picked, with one caption in its `text`. Clients show the photos and videos of a message as one tiled block (rows of up to four, each item as wide as its shape needs so a row has one height) with the caption underneath, and a single photo the same way. Tapping an item opens a full-screen viewer that swipes between the items. All of this is presentation: the album is the existing sealed message, and the server sees nothing new. (Messages from before this rule may still carry a small `thumb`; it is ignored.) A descriptor without `v` is media from before stage 6: it was encrypted with the chat key of the post's epoch, with associated data `<mid>:<i>`, in 180 KB pieces, and `hash` is over the whole file. Such media stays readable through the same HTTP path; nothing is migrated.

**Tickets: the room-key gate over HTTP.** An HTTP request carries no chat level of its own, and room keys never travel over HTTP. A proven connection that holds a level for a chat asks for a ticket with `media.ticket { cid }` and gets `{ t, exp, limits }`: 24 random bytes, valid for `ticketTtlMs` (10 minutes) and only for that chat, held in memory only and bound to that connection. Each HTTP request sends `Authorization: Hush <t>`. The server then checks the connection's **current** level for the chat on every request, exactly as a socket operation would (5.4): a rotation, an admin change or a removal ends access at once, and a ticket dies with its connection. A client renews a ticket shortly before it runs out, or when a request answers 401.

**Routes.**

| Request | Needs | Answer |
|---|---|---|
| `GET /media/limits` | nothing | `{ ok, limits }`: the media limits of 9.2, for the client to check files before sending |
| `PUT /media/<cid>/<mid>/<i>` body: iv and ciphertext; optional `X-Hush-Exp: <ms>`; `X-Hush-Oh: <64 hex>`, the SHA-256 of the uploader's media token (HKDF of the account's own secret, salt `hush-media-own-v1`, info `<cid>|<mid>`), kept with the media id when it is born and never rewritten (optional until every page sends it; then required) | member (admin in a channel) | 201 stored, 200 the same bytes were already stored (a retry). Pieces are write-once: different bytes for a stored piece answer 409, so no member can swap a piece of someone else's file; a piece under an id whose stored hash differs answers 403, so nobody grafts onto someone else's file |
| `GET /media/<cid>/<mid>/<i>` | member | the piece as `application/octet-stream`, `Cache-Control: no-store` |
| `DELETE /media/<cid>/<mid>`; optional `X-Hush-Ot: <token>` | member of a DM; in a group or channel the holder of the media token (its hash matches the one kept with the id, compared in constant time) or an admin; an id kept without a hash is an admin's alone | `{ n }`: every piece of that media id removed |
| `POST /media/<to>/<mid>/copy` with `X-Hush-From: <cid>/<mid>` and `X-Hush-From-Ticket`; `X-Hush-Oh` the forwarder's hash for the copy | member of the source; member (admin in a channel) of the target | 201 copied, 200 already there. A forward: the server copies the pieces to a new id in the target chat, and the sealed descriptor is reused with that id, so nothing is downloaded or uploaded again and each copy can be deleted or expire on its own; the copy is the forwarder's, not the source's uploader's |

Refusals: 400 `invalid`, 401 `unauth` (no, unknown or expired ticket), 403 `denied` (no level, or the ticket is for another chat), 404 `notfound`, 409 `conflict`/`exists`, 413 `toolarge`, 429 `ratelimit`, 507 `full`. A 507 body carries `scope`: `chat` when the chat's own allowance (`chatBytes`) is used up, so deleting something in that chat helps; `server` when the disk floor or the server-wide cap (`maxMediaBytes`) refuses, which no delete of the sender's own will cure soon. Every answer carries `Cache-Control: no-store` and `X-Content-Type-Options: nosniff`. Cross-origin requests are answered for the allowed origins (`Authorization`, `X-Hush-Exp`, `X-Hush-From`, `X-Hush-From-Ticket`, `X-Hush-Oh`, `X-Hush-Ot` headers; `GET`, `PUT`, `POST`, `DELETE`).

**Disappearing messages.** When a chat has a message timer, the client uploads with `X-Hush-Exp` set a little after the message's own expiry. The server keeps, per media id, the latest such time (and keeps the media for good once any piece came without one, so a piece is never swept before the message that shows it), and the expiry sweep (8.6) deletes the media when it passes. The server already sees the expiry of every disappearing message (5.7), so this reveals nothing new.

**Clean-up.** Deleting or expiring a message deletes its media; in a group or channel the uploader's delete (with the media token) or an admin's removes the pieces. The server never learns who uploaded what: each media id keeps only the hash of a token derived from a secret the server never sees, with a different derivation per id, so two uploads by one person are unlinkable and no media id is linked to any post; at delete time the server learns only that the deleting connection held that id's token, the same as a post's own-token already shows. A member's delete of media stored before the token existed (no hash) leaves the pieces to the chat's allowance. An upload that cannot finish deletes what it had stored. A message that was never sent after its media went up leaves the media behind; it counts against the chat's allowance until the chat is deleted. The server keeps no link from a message to its media, by design.

## 8. Storage

### 8.1 Tables in hush.db

```
docs      (path TEXT PRIMARY KEY, parent TEXT, id TEXT, d TEXT, ts INTEGER, exp INTEGER)
          index (parent, ts), index (parent, id), index (exp) where exp > 0,
          index (last.exp) where parent = 'channels' (release 91)
chats     (cid TEXT PRIMARY KEY, type, visibility, epoch INTEGER,
           cap_m TEXT, cap_a TEXT, cap_o TEXT, lv TEXT)
          index (visibility)
wraps     (cid, tag, e, n, ts, PRIMARY KEY (cid, tag, e))
search    (h TEXT PRIMARY KEY, n TEXT, n2 TEXT)   index (n), index (n2)
```

`chats.lv` (release 91): a channel's leave rotations of the last day, a JSON list of the server's times (5.6). `wraps` (release 91): per channel and epoch, how many wraps an account (a keyed tag, 8.3) added outside `chat.rotate` (5.4) since `ts`, the server's time of the first of them.

`docs` holds directory entries, chat records, posts, acts, reads, comments, key-chain rows and member cards (release 91), invites-by-reference, mailbox notes (`inbox/<h>/c/<id>`, section 6), and the blind-address collections. There is no separate mail table: a note is a document like any other, which is what lets the existing live subscription deliver it. `ts` is copied from the document's own `ts` field when present so that post pagination is indexable; the server adds no timestamps of its own.

### 8.2 Tables in media.db

```
chunks    (cid TEXT, mid TEXT, i INTEGER, iv TEXT, d BLOB, PRIMARY KEY (cid, mid, i))
media_ids (cid TEXT, mid TEXT, bytes INTEGER, exp INTEGER, oh TEXT, PRIMARY KEY (cid, mid))
```

`chunks` holds the encrypted pieces: since stage 6 they arrive over HTTP (7.7) as raw bytes, 1 MiB of plaintext each, written once. Pieces stored before stage 6 (180 KB, written over the socket) stay where they are and are read through the same HTTP path. `media_ids` keeps, per media id, only its stored size (for the per-chat allowance), for media of a disappearing message when it may be swept, and the hash of the uploader's media token (`oh`, 7.7; empty for media stored before it existed, which no later piece may claim); it was filled once from `chunks` when stage 6 first started. The socket may still read and delete pieces but no longer writes them.

The store is format-agnostic by rule, not by accident: no content type, file name, duration or "kind" ever appears in a row or in the path. A voice message, a photo, a video and a document look alike to the server; what a media id is, and the key that opens it, is known only to the sealed message that points at it. Limits are in 9.2.

Audio messages are media attachments and nothing more: the client records, encodes and encrypts the clip exactly as it does a photo. Browsers record with `MediaRecorder` at 32 kb/s, preferring AAC in MP4 (which every browser and phone plays) and falling back to Opus in WebM; the duration and a waveform are computed before encrypting and sealed in the descriptor. A phone app records AAC with the platform recorder and uses the same descriptor and the same upload path; the server needs nothing new for it.

### 8.3 Keyed blind addresses

Clients already address five things by secrets they derive themselves: `accounts/<loc>`, `logins/<tag>`, `phones/<hash>`, `vault/<id>`, and `backup/<id>` (the backup moves from `backup/<handle>` to a blind address derived like the vault's, with label `hush-backup-id:`). Message backup, the chat-key store kept in that box so a fresh login brings past messages back, is on by default for accounts created from stage 7 on; accounts from before keep whatever they chose, and the switch stays in Settings, Advanced. From release 19 a save never replaces the backup: the device reads it, takes the keys it lacks, adds its own, and writes naming the version it merged (9.3); every app open with Message backup on does the same, so a device that is already signed in picks up keys another device backed up. Turning it off asks first and says that it deletes the backup from the server. Before a device creates a backup from nothing it reads the setting fresh from the vault, so a device left open while another turned it off doesn't put one back; the switch saves the setting before it deletes. A backup this account's keys can't open is left alone, and the person is told once (nothing offers to delete it: a device with out-of-date keys could wipe a backup the other devices still open). A device that can't open some older messages is told so once, with what brings them back. Today those addresses are plain SHA-256 outputs, which a thief with the database can brute-force for phone numbers and weak logins.

The server therefore stores and looks up `HMAC-SHA-256(addr.key, address)` instead of the address, with `addr.key` a 32-byte secret kept at `/etc/hush/addr.key`, readable only by the service user, excluded from database backups and backed up separately. Stealing the database alone yields nothing reversible; stealing both reduces to today's situation. The same keyed form names a member card (`roll:` + cid|h) and an account's wrap count in a channel (`wrap:` + cid|h), release 91.

### 8.4 In memory only, never on disk

Presence (last-seen per handle, expires after 24 hours), typing rows (expire after 15 seconds), connection sessions, chat levels, subscriptions, rate-limit buckets, the hourly address salt.

### 8.5 SQLite settings

WAL journal, `synchronous = NORMAL`, `secure_delete = ON` so deleted rows are zeroed, `foreign_keys = ON`, busy timeout 5 s, one writer (the single Node process), weekly `VACUUM` at a quiet hour, nightly backup through the online backup API.

### 8.6 Background jobs

| Job | Interval | Action |
|---|---|---|
| expiry sweep | 1 min | delete posts and comments with `0 < exp < now`, each post with its acts and comments (at most `sweepSideMax`, 5000, of those per run past its first post; the rest wait for the next minute), and member cards 30 days after they were written (release 91); clear a chat's `last` once its own `exp` has passed, found through its index (release 91); delete media whose `media_ids.exp` has passed (7.7); forget expired media tickets |

Restoring a backup costs, on every device that saw a private channel's key change made after it, that channel: the device refuses the restored record as a rollback (posts, lists, links and key changes; the owner's name, description and admin list still save), and nothing in release 93 brings it back (Phase 3's restored mode); groups and one-on-one chats are unaffected (5.6 "Key chain") |

### 8.7 Reports

Anyone signed in may report a post in a public channel (`report.send`, 7.1) as spam, abuse, illegal or other. Whether a chat is public is decided from the server's own record (its frozen `type` is not `dm` and its `visibility` is `public`), never from the request, so a DM or a private chat can never be reported, even a DM a crafted client created with `visibility: public` before release 107. Since release 107 only a channel is made public or marked public (5.3); a group a crafted client made or marked public before that stays so, and its posts can be reported. The table is the server's own, like `bans`; no document path reaches it:

```
reports   (id TEXT PRIMARY KEY, ts, exp, cid, pid, reason, name, post, key, tag TEXT UNIQUE)
```

A row holds the time, an expiry 90 days later, the chat and post ids, the reason, the chat's public name at that moment, the server's own copy of the stored post (nothing the reporter sent), and the published key of that post's epoch (`openKeys[e]`), so the report can still be read if the channel later turns private or is deleted. It never holds the reporter: only `tag = HMAC(addr.key, "report:" + handle | cid | pid)`, unique, so the same person reporting the same post again changes nothing. Reports are read with `report.list` by the usernames in `HUSH_OWNERS` and nobody else, and the tag is never sent. The hourly sweep deletes rows past `exp`, and `report.list` never returns one.

What this reveals: the server keeps, for 90 days, a copy of a post it could already read (a public channel publishes its keys in `openKeys`), with the reason, even after the post is deleted or a disappearing message expires. A copy of the database without `addr.key` can't tell who reported. A live operator, who holds `addr.key`, can test whether a guessed username reported a given post, exactly as with block tags (5.6, 10.4 A2), and sees the proven handle of the connection sending each report while it is running.

|---|---|

The server enforces the piece size, the piece count, the per-chat allowance and the disk guard. The per-kind sizes can only be checked by the client, since the server never learns the kind; they are the client's rules, published by the server so there is one place to change them.

### 9.3 Schema rules per collection

- `directory`: must contain `handle == <h>`, `ecdh{x,y}`, `sig{x,y}`; optional `name, disp, bio, photo, devs, findable, requests, kv, ts`. `prev`, the key history (4.2), is the server's: at most eight `{ sig{x,y}, until }`, appended by the server when `kv` rises; a client write that would change it (a new entry that brings one, an `update` naming it, a `set` with a different one) is refused with `denied`, and a `set` without it keeps the stored one.
- `channels/<cid>`: fields from 5.3 only; no-names denylist; `type` and `visibility` enumerated; `epoch` integer; `keys` and `akeys` values are exactly `{ epk{x,y}, iv, ct }` and `meta`/`ometa` exactly `{ e, iv, ct }`, and `chat.join`, `chat.rotate` and `chat.admins` check the record they produce as an `update` does, so nothing a member adds can make a later write fail; whenever `meta` is written (create, update, `chat.rotate`) its `e` must equal the record's epoch after the write; whenever `ometa` is written its `e` must be at most that epoch; the `ct` of `meta` and `ometa` is at most 256 KB and an invite (`{ iv, ct, ph, ts, as? }`, `as` at most 256 characters, release 91) has a `ct` of at most 8 KB, and an update may not take `invites` past 50 links (`toolarge`), and an update that grows `keys`, `meta` or `invites` stops 300 KB short of the record's limit, so nobody pads the record until the owner can't write `ometa` (a removal's rotation clears invites and replaces `meta`).
- posts: exactly the shapes in 5.7; `e` an integer 0 to 2^31−1, in a channel the current epoch (5.7, release 91; the old "`e <= epoch`" was never checked). A new post's `ts` lies within 30 days back and 400 days ahead of the server's clock; an update keeps `ts` unless the stored one is in the future or less than a minute old (a scheduled message sent early), and then only to a time within that same window (release 21: a back-dated edit would otherwise make an old-key signature check out past the key history's window, 4.2). In a chat with a `ttl` a sealed message's `exp` is at most `max(ts, server time) + ttl` with a minute's allowance, or the stored `ts` and `exp` are kept (5.7).
- acts: id pattern and key set `{ post, kind, e, iv, ct, ts }`, all required except `e`; in a channel `e` is required and is the current epoch (release 91). From release 18 the author’s signature travels sealed inside `ct` with what it signs, so nothing stored ties a reaction or a poll vote to an account key; a plain `sg` is refused.
- a channel's acts through `chat.act` (since release 97): `{ post, kind, e, iv, ct, an }`, `an` always 1, no `ts`, `iv` 12 bytes and `ct` 80 bytes in plain base64 (5.7).
- reads and typing: id `^[0-9]{1,10}~[A-Za-z0-9_-]{22}$` (one or two digits before release 91), body exactly `{ ts, iv, ct }`: the signature over the chat, the tag and the time is sealed under the chat key (release 18), so only people in the chat can check it; a plain `sg` is refused.
- key-chain rows (`channels/<cid>/chain/<e>`, release 91): exactly `{ c }` at epoch 0; above it `{ b, c }`, or `{ c }` from a connection at owner level for the channel (release 93), base64 (5.6).
- member cards (`channels/<cid>/roll/<tag>`, release 91): exactly `{ e, iv, ct, ts }` or `{ iid, iv, ct, ts }`, `ct` 528 bytes, `ts` the server's (5.6).
- media piece: over HTTP, a body of at least 28 bytes (iv and tag) and at most `pieceBytes + 28`; stored as `{ i, iv, d }`. Nothing else, ever: no content type, size hint, file name, duration or kind. Whether a media id is a photo, a document or a voice message is known only to the sealed post that references it. The only per-media facts the server keeps are in `media_ids` (8.2): total size, an optional expiry and the hash of the uploader's media token (7.7), which names nobody.
- `accounts`, `vault`, `backup`: exactly `{ iv, ct }` or `{ iv, ct, ts }`.
- `backup` writes (release 19): a `set` names the version it was merged from, `was` in the request: the stored `ts`, or 0 when there is none. Anything else is refused with `conflict` (the page reads, merges and tries again, up to six times) and a missing or non-number `was` with `invalid`; an `update` is never accepted. `was` is checked and never stored, and it is a time the server already holds. The page writes `ts` as the later of now and the stored `ts` plus one, so versions only go up.
- `inbox/<h>/c` (section 6): a note is `{ epk, iv, ct, ts }` with `ct` of the one fixed size, plus `own: 1` on a note the owner writes to themselves, which only they can do over the socket. From release 21 such an own note is not charged to the connection's note bucket (9.4): the mailbox holds at most `inboxMax` notes anyway, and the page re-writes its whole chat list after a key change.
- `logins`: exactly `{ ts }`.
- `phones`: exactly `{ handle }`.
- `linkreqs`: from release 58, link asks (14.14): `ask` (written by the new device before it signs in, at `offerTag(n)` only, with exactly `{ state, ts, n, pub, devk, dev? }`: its one-time key, its device key `devk` (`{ id, x, y, sx, sy }`, the id of `devs` and four strings of at most 128), its name, and no `h`; every field is capped, so an ask is under 1 KB), then `ok` or `no` (answered once, by any signed-in account, which names itself in `h`); the asker takes it down, and anyone may once it is answered. From release 16, link offers (14.14): `offer` (opened by a signed-in account, naming itself in `h`, at `offerTag(n)` only), then `wait` (claimed once by the device that scanned the code), then `ok` (answered only by the account that opened it); the account takes it down, or the new device clears it once answered. The records below, at a login’s tag, are what the pages wrote before release 16: still readable, but from release 16 nobody writes, answers or removes one (the emailed codes that opened them are gone, and a box found at the gate proves nothing, since anyone may store one). States `wait`, `ok`, `no` carry the fields the client writes today, in offers and old records alike.
- `presence`: `{ ts }` or `{ hidden: true }`; hidden deletes the in-memory entry.
- `search`: `{ h, n, n2 }`, `h == <h>`, strings ≤ 60 lowercase.

### 9.4 Rate limits

Buckets live in memory. "address bucket" means a token bucket keyed by `HMAC(hourlySalt, remoteAddress)`; the salt is random, rotates every hour, and is never written anywhere, so the key cannot be reversed later. The address is read from Caddy's forwarded header, used for the HMAC, and discarded. From release 62 an IPv6 address is counted by its /64 (the first four hextets; an IPv4 address, mapped into IPv6 or not, by itself), since one home or phone holds a /64 and a count per /128 would be no count at all.

| What | Key | Limit (initial, tunable) |
|---|---|---|
| `hello`, `prove` | address | 30 / min; 10 failed proofs per 10 min then 10-minute block |
| `accounts`, `logins`, `phones`, `recovery` reads | address and per path | 20 / min per address, 60 / h per path (`blindReadsPerMinPerAddr`, `blindReadsPerHourPerPath`); `get` and every path of an `mget` alike, proven or not |
| `linkreqs` reads | address and per path, counted apart from the row above | 120 / min per address, 2000 / h per path (`linkReadsPerMinPerAddr`, `linkReadsPerHourPerPath`). A new device polls its request every 3 s for up to 5 minutes and each device that may let it in polls every 3.5 s, and several of them share one network address, so the strict count above starved them. A request holds only the asking device's public key, its name and the sealed handoff |

## 10. Threat model

### 10.1 Assets

Message and media content; group membership and the social graph; the mapping of real-world identifiers (phone, email) to handles; account recovery blobs; availability.

### 10.2 What the server stores, by sensitivity

| Stored | What it reveals |
|---|---|
| directory entries | public profiles and public keys, by design; for a deleted account (4.7), only its username, public keys, key history and the time it was deleted |
| opt-in search and phone entries | that a person chose to be findable; phone entries are keyed-hashed at rest |
| chat records | random ids, type, public or private, epoch, how many wraps exist (roughly members times devices), hashes of room keys, sealed metadata, activity time of the last message, and for a channel the times of its leave rotations in the last day (release 91), and for a private channel its exact subscriber count `n`, a number and no names (since release 96) |
| member cards (release 91) | per private channel, one sealed card of one size per account that wrote one in the last 30 days, its time, and for a join request which link; who wrote it only as a tag keyed under `addr.key` (5.6, 8.3) |
| key-chain rows (release 91) | per channel and epoch, two sealed blobs |
| wrap counts (release 91) | per channel and epoch, how many wraps each account (a keyed tag) added outside a key change |
| chat bans | per group or channel, how many usernames its admins blocked, as tags keyed under `addr.key` (5.6, 8.3): who they are can't be read from the database alone |
| reports | for 90 days, a copy of each reported public-channel post, that epoch's published key, the channel's name and the reason; the reporter only as a tag keyed under `addr.key` (8.7) |
| posts, acts, reads | per chat: times, sizes, pseudonymous tags, ciphertext |
| media pieces | per chat: how many media ids, their sizes and piece counts, when they were uploaded, and for media of a disappearing message, when it expires; never what kind of file, its name or its key |
| mailbox notes | recipient handle, hour of receipt, an opaque 1 KB blob, and whether the owner wrote it to themselves; someone else's note until the owner deletes it or 30 days pass, the owner's own until they delete it |
| account, vault, backup boxes | ciphertext at keyed-hashed addresses |
| link requests | for up to 10 minutes, a sealed device-handoff blob at a keyed-hashed address |

### 10.3 What the server never stores

IP addresses; which handle is in which chat (blocks are kept only as tags keyed under `addr.key`, 5.6: a copy of the database without that key can't tell who is blocked); who reported a post (only a tag keyed the same way, 8.7); who sent any post; who talks to whom; which handles share a device or connection; message content, names of private groups, member lists, contact lists; receipt timestamps other than the mailbox hour; access logs of any kind.

### 10.4 Adversaries and outcomes

**A1. Someone steals the database or a backup.** Gets everything in 10.2 and nothing in 10.3. Cannot reverse phone or login addresses without `addr.key`. Cannot open any box or message.

**A2. A curious operator watching the live process.** Additionally sees, per connection, the proven handle, which chats it opened, and the network address. Can therefore reconstruct membership over time by watching, and sees the username in each `chat.ban` and, from release 93, the usernames an owner's or admin's page asks `chat.slots` about for a channel id, which are the authors of the cards it read (it could already work these out from the roll with its own `addr.key`, and nothing durable records them); with `addr.key` it can also test usernames against a chat's block tags, and against report tags to learn whether a guessed person reported a given post (8.7). Nothing durable records membership, and the design keeps sender identity off the mailbox path, but this adversary is only partly defended against. Full defence requires network anonymity, out of scope.

**A3. A malicious server**, or anyone who can write its database. Can refuse service, delete or reorder data, serve stale chat records, and withhold key rotations. Can read new messages in private groups and one-on-one chats, by serving a key change with a key it chose, wrapped to the members' public keys. Nothing signs or announces a group or one-on-one key change, so pages accept it and seal new messages under that key from then on. The server then reads those messages, with their media keys, service notes and call setup, and the names and member lists written afterwards. Security codes, even when checked, do not stop this, because they cover account keys, not chat keys. Messages sealed before the switch stay unreadable to it. Private channels refuse such a key change on a device that has seen the channel's key chain and holds the owner's signed admin list (5.6), but not on a device seeing the channel for the first time. Since release 93b a device also refuses a private channel's record older than a key change it checked or made (5.6 "Key chain"), so a server serving an older record cannot have it seal under a key someone removed since still holds; a device at first sight has no such mark. A fix is being decided. Cannot forge posts (inner signatures), inject members without a wrap that the invitee's device can open (it has no device private keys), or impersonate a handle (no account private keys). Two replays that would have let it re-admit a removed member through an honest admin's client are refused by the client (5.3): a copy of an older epoch's wrap presented as the new epoch's, and sealed metadata from before the removal. Today it also serves the page itself, so it can serve altered JavaScript; see 10.6.

**A4. Network attacker.** TLS 1.2+ with HSTS. An origin is allowed if it is listed in `HUSH_ORIGINS`, or is a page served from the host the request came to (the `Origin`'s host equals the `Host` header, scheme aside, since Caddy ends TLS). `HUSH_ORIGINS=*` turns every origin check off, for tests and non-browser clients only. The WebSocket upgrade refuses any other `Origin`, and a missing one, with 403. From release 93, `POST /drop` and `POST /wake` answer 403 to a request whose `Origin` header is present and not allowed, `null` and an empty value included. The body is `{ ok: false, e: "denied", m: "drop: origin not allowed" }` (`"wake: origin not allowed"` on `/wake`), and no CORS headers are sent, so another site's page can't read it. The checks run in this order: `OPTIONS` gets 204 (CORS headers only for an allowed origin), any method but `POST` gets 405 `invalid`, then the `Origin` check gives 403 `denied`, and only then is the address tagged and charged and the body read. A refused request therefore reads no body and spends no allowance (not the address, ticket or recipient buckets of 9.4), sends no push and files no note, and the 403 never depends on the ticket or the recipient, so it reveals nothing about either. A request with no `Origin` header is processed exactly as before, so `curl` and the install scripts' `POST /wake` check still get 204. Every current browser sends an `Origin` on a cross-site POST, while a non-browser can write any `Origin` it likes, so refusing a missing one would protect nothing. Non-browser callers stay bounded by the address buckets. An allowed origin gets the same answers as before. `/media/*` is unchanged: another origin only loses its CORS headers (no 403), and everything under it but `GET /media/limits` needs a ticket, which is issued only over the origin-checked socket. The service takes a client address from `X-Forwarded-For` only when told it sits behind Caddy (`HUSH_TRUST_PROXY=1`); otherwise it uses the socket's own, so nobody reaching Node directly can forge their way out of the address limits.

**A5. A member with a tampered client.** Holds valid room keys for their chats. Can spam them within rate limits, overwrite tagged side rows, add wrap entries for outsiders (visible to other clients as unexplained wraps), and ignore client-side rules such as the one-message request limit. Since release 108 the recipient's own page decides what is a request and holds the invitations of new people (section 6, "Who left a note decides what it is"): with "Send a request first" on, leaving the `request` tag out no longer gets a changed client a normal chat, an unread count, a ring, a call ticket or a read mark, and its extra messages are counted, not shown; an unsigned invitation is dropped, and a signed one from a person the recipient has no one-on-one chat with waits for Join. It can still write a stranger's username and a wrap into a chat record, store messages nobody is shown, and, where the recipient has the setting off, get round the hold with one one-on-one note first (section 6, "What this does not do"). Cannot act in chats they are not in, forge another member's posts, or change settings that need an admin key.

**A6. An outsider.** Can enumerate handles through the directory at 600 per minute per connection (9.4), test whether a login exists at 20 per minute, probe account boxes at the same rate, drop mail into any mailbox within limits, and create accounts at the cost of one puzzle each, 10 a day per address (100 before release 62). Can also reserve a login or a phone entry that is not theirs, since neither is verified yet (open item 14.10, stage 8). Account boxes already require guessing login and password through 600 000 PBKDF2 iterations client-side per attempt. Recipient-side filtering (contacts only, block) handles unwanted drops.

**A7. A lost or stolen device.** Every device of an account holds the account's private keys, so taking its entry off the profile alone would change nothing; removing it (release 21; 14, item 15) replaces the account's keys. What the device loses at once: the server, which refuses its proofs and closes its connections (4.2); every DM, which gets a new epoch and a new base key (5.1); every group and channel the remover owns, which gets a new owner key and a fresh admin secret and, when private, a new epoch; every private group it administers, which gets a new epoch; the vault, the message backup and the password boxes, which move to new addresses under new keys and a new password; and the recovery words, whose boxes are deleted. What it keeps: the old keys and everything they opened while it had them, so its copy of the old vault and backup and the messages it had read; the keys of groups where the remover is only a member, which it reads until an admin rotates them; and the admin secret of groups the remover administers but does not own, until the owner changes admins. For the 30 days in which the server still accepts a post dated before the change (5.7), a message so dated in a chat that was not re-keyed can't be told from one the removed device wrote afterwards, since it signs with the old key that `prev` still vouches for up to that time. Whoever replaces the keys first keeps the account: a thief who does it before the owner locks the owner out, because the old keys, and the recovery words that hold them, are refused from then on; the same holds chat by chat for a DM's base key and a group's owner key (5.1), which the page therefore replaces right after the account keys and reports as lost when someone got there first. Pre-change messages in chats that were not re-keyed stay editable and deletable by the old ownership secret, which the device holds (5.7); the owner keeps that secret too. So a lost device is removed as soon as it is missed, and the recovery words are kept safe.

### 10.5 Properties this design gives up relative to Firestore rules

Identity-based refereeing inside chats (one request message, bans on public joins, who may answer a request; since release 108 the recipient's page keeps the first of these for itself by showing one text message only, section 6, and the server still referees none); exact `null` storage semantics; offline cache; managed uptime.

### 10.6 Trust in the delivered JavaScript

The service that stores ciphertext also serves the page that decrypts it. A compromised server could ship a backdoored page. Mitigations in order of cost: every file the page loads (its own `app/*.js` and `app/styles.css`, and the vendor script) carries an `integrity` attribute in `index.html` with the SHA-256 of its bytes, kept current by `npm run csp` and checked by the tests, so the browser refuses a changed file and publishing the SHA-256 of each released `index.html` still pins the whole app (the same tool writes a version made from the hash into each file's address, and Caddy marks `index.html` for revalidation on every visit and the versioned files as immutable, so a returning visitor never pairs a new page with a cached old file, which the pins would refuse and leave blank); serve the static app from a different operator than the API (for example a static host) and point the Content-Security-Policy's `connect-src` at the API domain, so that the API operator cannot alter the app silently; eventually an installable build. The owner should pick one before public launch (open item 14.3). Publishing the hashes is the release transparency item of 16.4; keeping anyone from changing the code in the first place is the rest of that checklist.

## 11. Logging, privacy operations and the server itself

### 11.1 Logging policy

- Caddy: no `log` directive, so no access log, for every route including `/drop` and `/media/*`. Its own log goes to journald without the two loggers that print a request's details (`http.handlers.reverse_proxy`, `http.log.error`; from release 17), so no visitor address, path or browser is recorded there. Media responses are never cached (`Cache-Control: no-store` from the service) and not compressed (ciphertext does not compress).
- Node: no request logging. Error log lines contain an error code and a stack trace, never a path segment, handle, chat id or address. Uncaught exceptions do not dump memory. Two lines of numbers only, from release 62: `media.disk { ok, freePct }` when the disk guard flips (so a refusal wave has a cause in the journal) and once per process with `freePct: -1` when statfs cannot be read (the guard then allows and says so), and `media.stats { bytes, ids }` once a day from the hourly sweep (all media stored, and how many media ids), the only size the server reports about its own data.
- journald: `SystemMaxUse=200M`, `MaxRetentionSec=14day`.
- Metrics: counters only (connections, frames per second, database size, free disk), exposed on localhost for the owner.
- No third-party analytics, fonts, CDN or error-reporting services anywhere.

### 11.2 Host hardening

- Ubuntu with unattended security upgrades; `ufw` allowing 22, 80, 443 only (plus, for calls, the relay ports: 3478 udp and tcp, 49152-49651 udp); SSH keys only, root login off. The owner's checklist for these, and for the places outside the server from which the code can be changed, is 16.4 (stage 8). That port list is the baseline up to stage 9. Stage 10 adds one UDP port range for the call relay (section 16); hardening scripts and alerts written before then must treat the firewall list as configuration, not as an invariant that any extra listener violates.
- Service runs as user `hush` under systemd with `ProtectSystem=strict`, `ProtectHome=yes`, `PrivateTmp=yes`, `NoNewPrivileges=yes`, `ReadWritePaths=/var/lib/hush`, `Restart=always`.
- Full-disk encryption is not available on a standard Hetzner VPS image without a custom install; the owner decides whether to use an encrypted data partition unlocked at boot by hand (open item 14.4). Keyed addresses and ciphertext-only storage limit what an unencrypted disk exposes.
- Time kept by `systemd-timesyncd`; clock skew affects expiry sweeps.

### 11.3 Caddy duties

Terminate TLS for `<domain>`, redirect 80 to 443, send `Strict-Transport-Security`, `X-Content-Type-Options: nosniff`, `Referrer-Policy: no-referrer`; serve `/srv/hush/www` with the app files and correct types, `index.html` as `Cache-Control: no-cache` and the versioned files under `app/` and `vendor/` as immutable (10.6); proxy `/ws` (WebSocket), `/drop`, `/media/*` and `/healthz` to `127.0.0.1:8080`; pass the client address only in the forwarded header the service uses for the salted bucket (the unit file sets `HUSH_TRUST_PROXY=1` for that; without it the service uses the socket's own address); no compression on the WebSocket or on `/media/*`; request bodies capped at the edge (release 62): 2 MB on `/media/*` (a piece is 1 MiB plus its 12-byte iv and 16-byte tag) and 16 KB on `/drop` and `/wake` (`request_body … max_size` in the Caddyfile), so an oversized body is cut off before it is read into the service.

### 11.4 Deployment layout

```
/opt/hush/server/        service code, owned by root, read-only to hush
/srv/hush/www/           index.html, app/ (the page's own files, 12.1), vendor/, manifest, icons
/var/lib/hush/           hush.db, media.db, WAL files      (owner hush, mode 700)
/etc/hush/addr.key       32 random bytes                   (owner hush, mode 400)
/etc/caddy/Caddyfile
```

Releases are a `git pull` plus `systemctl restart hush`. Database schema changes run as versioned migrations at start-up.

### 11.5 Monitoring (built 2026-10-12)

Two dead-man's switches at Healthchecks.io, each a check with a random ping address kept root-only in `/etc/hush/monitor.env`; the pings carry that id and, on a failure, a short reason, never user data. The provider learns the check ids, the ping times, the server's address and those reasons.

- `hush-backup`, expected once a day (grace 3 hours): the nightly backup (8.6) pings it after a successful upload, or its `/fail` address with the reason. A failed or skipped night becomes an email to the owner.
- `hush-watch`, expected every 5 minutes (grace 5 minutes): a systemd timer runs `/usr/local/sbin/hush-watch.sh`, which checks that the service is active, `/healthz` answers `ok`, the journal has no error or warning lines in the last 5 minutes, and the data disk has over 10 % and over 2 GB free. All four pass: one ping. One fails: a `/fail` ping naming it, and a `hush-watch` journal line. The server dead or offline: the pings stop, and the owner is emailed about ten minutes later.

Whoever holds a ping address can only hide a failure by pinging "ok"; it reads nothing. The addresses are rotated from the Healthchecks.io dashboard if they ever leak.

## 12. Client adapter contract

The adapter replaces `connectFirebase` and returns an object with the same shape as today so that the rest of the page is untouched:

- `collection(path)` with `doc(id?)`, `add(d)`, `where`, `orderBy`, `limit`, `get`, `onSnapshot`, `onSnapshotMeta`.
- `doc(path)` with `id`, `get`, `set`, `update`, `delete`, `onSnapshot`, `collection`.
- Snapshot objects with `exists`, `id`, `data()`, `docs`, `size`, `metadata.hasPendingWrites`, `metadata.fromCache`.
- `uid` is removed; `flat` stays `true`; `now()` returns the server-offset time.

Adapter responsibilities beyond translation:

1. Open the socket at page load, `hello` immediately, `prove` once an account is active, reconnect with back-off, and open a fresh connection when the active account changes. Since release 102: the wait before an automatic reconnect is a base (0.5 s after a `hello`, doubled up to 30 s each time an automatic attempt starts) plus a random part (up to 4 s, or up to 30% of the base when that is more), so that after a server restart every page is not back at the same moment. `present()` is the page's word that the user is here (the app came back into view, or a chat was opened): a reconnect that is waiting goes at once, and otherwise the next one a close starts within 5 s goes without the wait. One attempt per call, and an attempt the user asked for does not lengthen the automatic wait. A change from one account to another drops everything the account before had on the adapter, connected or not: its subscriptions, its calls waiting for a connection (they fail with `offline`) and its chat opens in progress.
2. For any path under `channels/<cid>`, ensure the chat is open on the connection first. It asks the app for keys through a small interface the app provides: `member(cid, epoch)`, `admin(cid)`, `owner(cid)`. If the app has no chat key yet, the adapter performs the preview read and hands `keys` to the app so it can trial-decrypt its wrap. From release 21 the app may hand back a list of keys, tried in order until one opens: for a DM its epoch key, then the base key the current account keys give, then the one from before a key change (5.1); for a chat the account owns the owner key, the one from before a key change, then its admin and member keys, so a chat whose owner key is no longer the account's still opens to read; when every key is refused the adapter forgets the chat's level, and an operation that needs a level fails with `denied` (or `ratelimit` while the server is busy) before anything is sent.
3. Emulate `hasPendingWrites`: on a local `set` or `add` under a subscribed query, deliver a synthetic snapshot with the pending document, then deliver the server's push without the flag. `fromCache` is always `false` in this version.
4. Batch concurrent `get` calls on `directory/*` and `presence/*` into `mget`.
5. Keep ordering and `limit` for subscriptions client-side after `init`.
6. Translate `sub` with `ids` for the chat list watcher.
7. Send nested objects as-is for `update`; the Firestore dotted-path flattening is removed.
8. Media over HTTP (7.7): `putPiece`, `getPiece`, `deleteMedia`, `copyMedia`, `mediaLimits`. 9. Key versions (release 21). The adapter keeps the `kv` of its `prove` reply (`kv`) and reports it to the page (`onKv`), which signs out when the server's version is above its own; a refused proof is reported too (`onDenied`), and the page re-reads its profile and signs out if its keys are stale. `rebaseChat(cid, cap)` and `setOwner(cid, cap)` open the chat and send `chat.rebase` and `chat.owner` (7.1).

The page was one file with one inline script until stage 7. It is now `index.html` (the markup, the policy, and the tags that load the rest) plus a folder `app/`:

|---|---|
| `app/styles.css` | every style the page had inline |
| `app/config.js` | `HUSH_CONFIG`, the server address the owner edits |
| `app/crypto.js` | keys and sealing: identities and device keys, the chat-key store and message backup, DM ids, key wraps and room keys, message and metadata sealing, side-channel tags and signatures, media encryption (the `HUSH MEDIA` block), recovery words and login boxes (`HUSH RECOVERY`, `HUSH AUTH`), the sign-in proof, the QR handoff bundle, inbox notes |

### 12.2 What the page keeps on the device (stage 7)

The page is built for a hostile browser environment: a copy of its storage, a shared or stolen device, a page left open.

**One sealed store.** Everything the page keeps under `hush:` lives in one map in memory and reaches disk only as one AES-256-GCM blob, `localStorage['hush:sealed']`: account and device private keys, the ownership secret, chat keys, invite secrets, the owner and admins of each private channel as this device last saw them (with `hk`, the owner's signing key that checked that list, and `n`, whether a copy of hers under her current key has narrowed it, 5.6 "Key chain"), the member cards it wrote (a `leave`, `dev` or `adm` card until its effect shows; a `join` card's link id and `m` until the chat is gone or refuses this account), the start's pass's stamps (when it last ran each private channel the account owns or admins) and who waits to join each such channel (5.6 "The start's pass"), logins, phone numbers, drafts, read marks, which chats were pointed to whom, the active account, and the chat list as last drawn (`hush:list:<handle>`: titles, last-line text, times and counts, at most 90 rows, so the list is on screen before the server answers; a channel with no post yet, for an account that is neither its owner nor an admin, caches only its kind, "Private channel" or "Public channel", never a number (5.3); a chat with a message timer, or whose last message disappears, caches no text, and nothing is written during a call), and the message timer last seen per chat (`hush:ttlSeen:<handle>`, so a timer the other side changed without a note can be pointed out). Since release 93b the roles record also holds `hi`, the highest epoch of a private channel whose key change this device checked, made or took from a link (5.6 "Key chain"), and, on the owner's device, `ak`, each admin's account key version the admin secret last went out to them under (5.6 "Member cards"). The waiting list of a channel, and `dk` in its roles record (the account key version of each author whose `dev` card this device last acted on, 5.6 "Member cards"), are an admin's to keep: once the chat watch sees the owner's list of that channel, as opened on this device, leave the account out while the connection holds no admin level there, both are dropped. A device removed from the channel while offline keeps them, hidden. Only the lock settings, the theme and the blob itself are stored plain. `sessionStorage` is not used. Several tabs of one browser share the blob: a tab that sees another tab's write takes the new map, and leaves an account that is no longer in it (logged out, or removed, in the other tab) without writing it back; a tab that can't open the blob any more, or finds it gone (the other tab replaced the device key when the last account left, or set a lock) reloads instead of writing; a tab whose account's keys another tab replaced (a device removal) reloads into them, and until it has reloaded it notes no copy of that account's own channel lists into the roles records the tabs share (release 92: it would check them against the key replaced, and the other tab would sign them again under the new one); and at start a blob the device key doesn't open is set aside under `hush:sealed:old`, so a stale write never leaves a page that can't start (release 21; before it, a logout didn't stick while another tab stayed open). The blob's key is:

- the lock password's key (PBKDF2-SHA-256, 600 000 rounds, a random salt) while a password lock is on, so the keys are unreadable without the password even to someone holding the whole storage; or
- otherwise a device key the browser made once, non-extractable, kept in IndexedDB. JavaScript can use it but never read it, and a copy of `localStorage` alone opens nothing. Where IndexedDB is unavailable the key sits next to the blob and the password lock is the real protection.

Turning the password lock on re-keys the blob under the password; turning it off re-keys it under the device key. Nothing is ever written out plain again. On first start after this change, the old plain entries are moved into the blob and removed; a blob that will not open (the browser lost the device key) is set aside, not deleted. Other tabs of the same page pick up each other's blob through the `storage` event.

**The lock.** With a PIN or a password set, the page shows the gate before anything is unsealed: no keys, no chat list, no messages exist in memory until it passes. Locking after time away is a reload, with a PIN just as with a password, so every unsealed byte (keys, decrypted messages and media, the screen itself) is gone the moment the lock falls. Five wrong tries back off; "forgot" clears the device.

**Logout.** Removes that account's entries from the store (keys, chat keys, login, drafts, marks, the invite secrets it made), takes the device off the profile, and drops everything unsealed from memory, including decrypted media and its object URLs. Logging out the last account also deletes the blob and the device key, and a fresh empty store is made. An account logged out elsewhere (its keys replaced on another device) is wiped the same way.

**No service worker.** The page registers none and must not gain one without rules: a future worker may precache `index.html`, `app/` and `vendor/` only, must never cache `/ws`, `/drop` or `/media/*` (which the server also marks `no-store`), and must never hold a decrypted byte. Decrypted media exists only as in-memory blobs with object URLs that are revoked on logout and die with the page.

Outside the page's control: the browser's own password manager, which is offered the Hush password only on the person's say-so, and the browser profile on disk, which is the operating system's to protect. On the iPhone app, Apple Passwords may save the username and password and fill them in at login (the site's `/.well-known/apple-app-site-association` names the app under `webcredentials`, and the app declares the matching associated domain); the lock screen and the lock-password fields are `autocomplete="off"` and never take part.

### 12.3 Badges and mentions (stage 8)

**Badges.** The operator decides who carries a badge, in `HUSH_BADGES` on the server, and nowhere else. The server sends the whole list in the `hello` reply (`badges: { "<handle>": "founder" | "verified" }`), and the page draws the badge after that person's name wherever a name is shown: the chat list, the chat header, the profile sheet, search results, member lists, and sender names in groups and channels. A profile document cannot carry a badge (9.3 refuses unknown fields) and the page never reads one from a profile, so nobody can give themselves one. The list is public by nature and names handles only.

**Report readers.** In the same way, `HUSH_OWNERS` on the server (comma-separated usernames, each `^[a-z0-9_]{3,20}$`, any other entry stops the server at start-up) names the operator's own accounts, the only ones `report.list` answers (8.7). Register those usernames before listing them: until one exists, anyone could sign up with it.

**Mentions.** `@handle` in a message is shown as a link wherever the page shows the text, in one-on-one chats, groups and channels alike. The link is made from the text alone: nothing is looked up because a mention is on screen. A tap looks the handle up (the same lookup the search box uses, by exact username, which finds anyone) and opens the one-on-one chat with that person under the usual message-request rules; a mention of oneself opens one's own Saved Messages; a blocked or unfindable handle shows a short notice.

**The picker.** Typing `@` and some letters in the message box offers a short list of people to insert. The list is drawn only from what the page already knows about the conversation: a group's members, a channel's owner and admins, the other person in a one-on-one chat. It never searches the server or looks anyone up, so it is instant and tells the server nothing about what is being typed. Matching prefers a username prefix, then a name prefix, then a word of the name, then anything containing the letters; at most six are shown. Arrow keys move, Enter or Tab inserts, Escape dismisses until the letters change.

## 14. Open items

1. **Domain name.** Caddy needs a DNS name for automatic certificates. The owner provides one whose A record points at the server (`<server address>`). The spec refers to it as `<domain>`.
2. **Proof of work on drops.** Decided in stage 5: on for recipients with `requests: true`, and for any recipient whose hourly allowance is half used (section 6).

15. **Replace the account's keys to lock out a lost device. Built in release 21 (live since 2026-10-12).** Decided 2026-10-11 as a must before public launch, for a recovery with the words; built for device removal first, because every device holds the account's private keys and taking a device's entry off the profile alone locks nothing. Removing a device (Settings → Login and devices → Your devices → Remove) therefore gives the account new keys: a new encryption pair, a new signing pair and a new ownership secret `own`, published under the next key version (`kv` + 1) in one write that also drops every other device entry. The server takes that write only over an account-key proof, appends the old signing key to the entry's `prev` (4.2), closes the account's other connections with 4401 and refuses the old keys from then on. The removing device then re-keys the chats first (every second until then is one in which the lost device's holder could replace a chat's keys himself, 5.1): every private group or channel it owns gets a new epoch, every owned one a new owner key (`chat.owner`) and a fresh admin secret (from release 92 also when its key change fails; in a private channel whose admin list this device holds unsigned, one from before release 92 the owner hasn't signed yet, say, the fresh secret is wrapped to her own devices alone (release 93b; before it none was made there), so the removed device's admin level ends at the removal, while the unsigned list is handed nothing and not signed: its admins are at member level until she saves the list, Edit, then Save, and her device next opens the channel or starts, and the summary says so, 5.6 "Key chain"), every private group or channel it administers a new epoch, a private channel whose key change it should make but couldn't has every open link stopped, and every DM a new epoch and a new base key (`chat.rebase`), so the old shared secret opens nothing; a DM whose other person's new security code is not yet accepted here is left for the acceptance (a base key from their old one would lock them out). Then it moves what the old keys guarded: the vault to the address and key the new keys give (the old one stays: vaults are never deleted, and it holds only what the lost device had already), the chat-list notes re-sealed to the new key, the message backup to its new address (merged with the old one first, the old one then deleted), the password boxes replaced under a new password it asks for (the lost device may know the old one, so the old one is refused), and the old recovery boxes deleted, so new words must be made. The old keys stay on that device, their private parts for 30 days, so old notes, the old vault and old messages still open and verify; other devices verify old messages through `prev`. The other devices are logged out and link again by code (item 14, path one). The flow is a stage machine kept in the sealed store and resumed at the next load, so a reload or a lost connection mid-way never loses the account; only a definite refusal of the key write rolls back to the old keys, and a device that finds the keys replaced from elsewhere meanwhile signs out.
    Limits, named in the summary the person sees: a group where the account is only a member keeps its key until an admin rotates it, and the removed device reads it until then (a private channel, from release 92, gets a `dev` member card, and a new key, which the removed device doesn't get, when an admin's device next opens it or next starts (5.6 "The start's pass"), or, when the page reads the channel's list and it doesn't name the account yet (waiting to join), its join card written again, signed by the new account key, and no new channel key: the removed device reads on until the key next changes, and the summary says an admin needs to add you, unless you came in through a link that is still open, which an admin's device lists by itself at its next open or start (a page that reads no list, a subscriber's once the server keeps it for admins, writes the `dev` card whether or not the account is listed; for an account not listed yet that card changes no key by itself: since release 104 an admin's page shows its author under Waiting to join, and once an admin has added them the next open or start changes the key; an open link no longer lists it: 5.6 "Member cards"); an admin's device that hasn't accepted the account's new security code leaves the account out of that key too, and the account's devices show the channel again once that admin's device accepts the code, if that is within 30 days of a device first finding the channel locked, 5.6); a group it administers but does not own keeps its admin secret in the removed device's hands until the owner changes admins (a private channel gets an `adm` card, also when its key change fails (an admin whose own `leave` card is still pending writes that card again instead, release 93b, and the owner's device then drops them and replaces the admin secret), and the owner's device replaces the admin secret and stops every open link when it next opens the channel or next starts, once it has accepted the admin's new security code and holds the channel's admin list signed (5.6 "Key chain"); since release 93b the owner's device replaces the secret once it sees the admin's new key version, whether or not the card is still there); a chat it owns whose owner key or admin secret couldn't be replaced can still be managed by the removed device: since release 104 nothing is tried again once the owner step has ended, the chat is marked "don't use" on that device for that account (`hush:noUse:<username>` in the sealed store, a map of chat id to 1, set where the owner step ends failed and taken off only where a later removal's step for that chat goes through), the summary names it in a red warning box ("Couldn’t secure these chats: <names>. A device you removed may still have control there. Don’t use them any more. Start new chats with the same people."), does not count it in "N chats are secured.", and the chat itself, if it is not one-on-one, says so in a line above its message box or read-only bar ("Couldn’t secure this chat. A device you removed may still have control here. Start a new chat with the same people."); sending is not blocked (before release 104 a grey line named the chat once, counted it as secured if its key change went through, and the chat then looked like any other). What is no failure of the step: a call answered `ratelimit`, `offline` or `unauth` ("sign in first") is waited out with no upper limit, the last after a fresh account-key sign-in, in the key-change loop as in the owner step; a refusal (`denied`) of an owner-step call counts only after a fresh open of the chat that answered below owner level (at owner level the step runs again, three times at most; an open that got no answer is waited out); the "out of date" error (the adapter closed for good) stops the removal as a closed tab would, with nothing filed or marked for the chat in hand, and the next start on a page the server accepts goes on ("Removing the device stopped (this copy of Hush is out of date). Close Hush and open it again to finish it."); after a call that got no answer at the admin secret of a private channel whose list is signed, once the owner key has landed, the page reads the record once, sends the admin secret no second time, and counts the step as done if the admin secret the server holds is the one this step made and the stop of the open links goes through then; a chat that no longer exists is not marked. After a sign-in refused for good (`denied`) during the chats stage the page reads the account's profile first. Where it shows a key version above this device's and a signing key that is not this device's (another holder of the new keys replaced them meanwhile; also met at the next start when Hush was closed during that stage), the removal ends and the device is signed out as any device with outdated keys is: with "Another device secured your account while this was running. This device can’t make changes any more." where another account is on the device, and with the removal's sheet closed where it was the only one (the sign-up screen then says why); the chat in hand and those after it are not secured. In every other case (the profile can't be read at that moment, has no entry, names this device's own key or shows no higher version, as after a server put back from an older backup, or another account is in use on the device by then) nothing is ended and the device stays signed in: the removal stops with "Removing the device stopped (<the refusal's words>). Close Hush and open it again to finish it." and the next start goes on with it. An account that isn't secured (the server gives it no owner rights) has every chat it owns marked in a removal. The mark's limits: it is on one device (another device of the account, or one linked later, shows nothing, and a log-out there erases it); a chat that failed in a removal before release 104 carries none; a second tab of a desktop browser that writes the store in the same moment can write it back without the mark; a removal run under a rolled-back page neither sets nor clears one. Not closed by release 104: a failed owner step is never finished unless a later removal's step for that chat goes through, so the holder of the removed device may keep owner or admin level there for good; where the owner key itself was not replaced, a second removal loses the owner right for good (the page is then at member level in its own chat, and no later removal changes that chat's key); a lost reply at the admin secret still marks a group, a public channel and a channel whose list was never signed, although nothing the removed device held opens the chat; nobody is told when a chat was marked wrongly; a group or one-on-one chat at epoch 31 can't be rotated (a channel has no epoch cap); a chat whose keys someone replaced first (the removed device, most likely) is lost and named, to be started afresh; for 30 days a message dated before the change in a chat that was not re-keyed can't be told from one the removed device wrote, and pre-change messages there stay editable by it (10.4, A7); every contact sees "security code changed", and their devices wrap nothing to the account until they accept the new code (their one-on-one chat with it is re-keyed on acceptance); invite links of the re-keyed chats stop working. Whoever replaces the keys first keeps the account, so a lost device is removed as soon as it is missed and the recovery words are kept safe. Already in place before: the page refuses a login whose keys are older than the profile's key version, and signs out a device whose keys are older. Still open: running the same replacement at the end of a recovery with the words, which this item first asked for.

## 15. Summary of guarantees for the owner's privacy statement

The Hush server stores encrypted messages that a copy of its database cannot read, public profiles, and the minimum needed to deliver data to the right people. It does not store IP addresses, access logs, chat membership, who sent which message, or who talks to whom. Group names and member lists are encrypted with the group's own key. People find their chats through an encrypted list only their own devices can open. Invitations arrive in a sealed mailbox that records only the recipient and the hour. When an admin blocks someone from a group or channel, the server sees that username in the request and keeps only a tag of it made with the server's own secret key, so a copy of the database shows how many people a chat has blocked, not who (someone who also holds that key could test usernames against it). A copy of the database reveals who has an account and how busy each chat is, and nothing else. A server that acts against its users, or anyone who can write its database, can do more: it can plant a key in a private group or one-on-one chat and read the messages sent after it (10.4, A3).

### 16.1 Audio messages (stage 6)

Built with stage 6. An audio message is a media attachment of kind `voice`. It uses the same pieces, limits, tickets and HTTP routes as any other file (7.7), and the server cannot tell it from a photo: pieces carry `{ i, iv, d }` and nothing else, and every descriptive fact about the clip (codec, duration, waveform) lives inside the sealed descriptor. Recording is described in 8.2; a clip may run 15 minutes (`voiceSeconds`).

### 16.2 Voice and video calls (stage 10)

Calls use WebRTC between the two clients for encryption and codecs, and nothing else from WebRTC's usual connectivity story. Specifically:

- **Media is relayed through our own server, always.** The service runs a relay (a TURN-style UDP listener next to the Node process, on the same host, not behind Caddy) and clients offer relay candidates only. Host and server-reflexive candidates are never gathered or exchanged, so neither party's client address ever reaches the other party. This is the whole point of stage 10's design and is not a fallback to be turned off for speed.
- **Signaling rides the existing WebSocket as memory-only call records, never as posts.** Built for one-on-one voice (calls stage 1). Offer, answer, end and mark each go to `channels/<cid>/call/<random 22-character id>` as `{ ts, iv, ct }` (`ct` at most 16000 characters, the whole record under the collection's 16 KB document cap, room for one audio and one video line): a side row like a typing mark, in one-on-one chats only, at member level, kept in memory for 60 seconds (`callTtlMs`) and pushed to the chat's watchers, never on disk, in backups or in a log. `ct` seals `{ e, p, sg }` under the current epoch's key with AAD `hush-call-v1|cid|<record id>`: `p` is the JSON of `{ v: 1, callId, kind, from, to, ts, exp, sdp?, reason?, tag?, video?, cam?, why? }` (`tag`: a random mark the answering device puts on its answer and its end, so another device of the same person can't end a call it didn't pick up) and `sg` the account signature of whichever side sends it (caller or callee) over `hush-call-v1|cid|e|p`. A page acts on one only if it opens under the current epoch, the signature is by the sender's current key, `from` is the other person and `to` itself, it is under 30 seconds old and not expired by the server's clock and within 10 minutes of the device's own, an offer is new (to this page, and to this account on this device: the ids of offers it was shown are kept a day, the last 200), and the sender isn't blocked, deleted or showing a changed security code. The 30 seconds trust the server's clock, so a malicious server could still replay, within those 10 minutes, an offer this device never saw: that rings, but can't connect, since the DTLS keys it named are gone with the old call. A page watches the newest 50 records of each chat, so a flood can't hide a new one. An offer a page can't use gets no reply, and a page on another call answers `busy` at most once a minute per person; a page whose app build is too old to take calls answers `old` the same way, and the caller shows why (16.5). So the records never show on disk that a call was placed; the live server does see a call record written by one person's connection in a chat with another, which is who called whom.
- **Video rides the same call, on a line set up from the start.** Every browser call's offer carries one video line beside the audio line, bundled on one transport (one relay allocation a side), with H.264 constrained baseline (profile 42e01f, packetization-mode 1) first and VP8 second, plus their resends, and with no camera on it, so turning video on or off never needs a second offer. `video` is 0 or 1: on an offer or an answer, that its side can do video; on a `mark`, that its camera is on. `cam: 1` on an offer says the caller starts with its camera on, and the callee's page rings "Incoming video call" if it can show video. `why: "net"` on a mark says a poor link turned the camera off. A `mark` from the callee counts only with the answer's `tag`, one from the caller only once this side has answered; a mark changes only what the other side shows, never ends a call and never starts a camera. A call has video only when both its offer and its answer carried `video: 1`. A description has exactly one `m=audio` line, at most one `m=video` line (a declined one, port 0, included) and nothing else. In a video call both cameras come on, as in FaceTime: the caller's for "Video call", the callee's as it answers an offer that said `cam: 1` (the offer's word alone: a mark the caller sends before the answer is ignored, and an Answer given on the iPhone's system screen while it still said audio, before the page named the call video, keeps the camera off and says so; a tap on Video while a camera is still starting cancels it); either side turns its own off at any time with Video. In a voice call every camera starts off and only that side's tap on Video turns it on. (Until release 88 a video call was answered with the callee's camera off.) Off stops the camera, never just disables the track, which would keep sending black frames with the camera light on. What a side sends is capped by its own network (release 89): on Wi-Fi or a wired link 1080p up to 4 Mbit/s, on a mobile network (or one the device can't name; a browser only when it says so) 720p up to 2 Mbit/s, on a TCP relay path 300 kbit/s, at most 30 frames a second, stepping size and rate down together on a weak link; a hot iPhone steps down further. (Until release 89: 640x480 at 24 frames, 600 kbit/s.) The far side's picture fills the screen when its shape is close to the screen's (the narrower of the two aspect ratios at least 0.7 of the other: a phone's 9:16 on a phone), and shows whole on black otherwise (a 4:3 webcam, a phone held sideways); this side's own picture fills the screen while a video call rings out and connects, then moves to the corner. Video turns off by itself, with a `mark { video: 0, why: "net" }` and "Video off: poor connection", when a side sends under 150 kbit/s for 10 seconds while the bandwidth holds its encoder back (a still picture on a good link sends little and is never held back), loses over 10 % for 6 seconds, or is held to 180 pixels by the bandwidth for 10 seconds, judged only once video has flowed and from 5 seconds after the camera started (or the call went live, if later); it comes back on by itself once a call, after 10 seconds of a usable link. A camera that has sent nothing in its first 10 seconds goes off with "Video couldn’t start on this call." and a plain off mark, and is not tried again. The far side's picture follows its frames: three seconds without one while its mark says on shows "Paused". Minimised, the far side's picture floats in a corner. The page never records, captures or casts a call track. The app lock never comes up during a call (a lock that falls due waits for the call to end, camera included); should one ever stand over a call, this side's camera is turned off. The iPhone app's plugin on every build before native video refuses a description with any line but audio, so its page hands the plugin a browser's offer without the video line and sends the plugin's answer on with that line declined (port 0, inactive): such a call is voice. The relay, the server and anyone on the path can tell a video call from a voice call by its volume and by the length of its offer, so "which kind of call" joins "who called whom" as what the live server can see. Marks count against the same call-record limit as offers and ends; a page sends at most one a second, and none without a change.
- **Each call leaves one entry in the chat, as an ordinary message.** When a call it placed is over, the caller's page sends one post through the usual path (sealed, signed, sealed sender, 5.7) whose body is the character U+0001 followed by the JSON of `{ text: "", call: { kind, secs, video? } }` (`video: 1` when a camera was on, on either side, at some point: "Outgoing video call · 3:12", "Incoming video call", "Missed video call"; older pages ignore it): `kind` is `ended` (answered; `secs` its length in whole seconds, 0 to 86400), `declined`, `missed` (no answer in 45 seconds), `cancelled` (the caller hung up first), `busy` (the other person's device was on another call and never rang) or `failed`. Only the device that placed the call writes it, so there is one per call, and none for a call whose offer never went out; a caller's page closed mid-call may not get it out, and one that switches account mid-call writes none (the next account would sign it). Pages read it only in a one-on-one chat, by one of its two people, and in exactly this shape; anything else shows as a plain "Voice call", and its text, media, reply and the like are ignored. It is shown by who is looking (the caller: "Outgoing call · 2:05", "Call declined", "No answer", "Cancelled call", "<name> was busy", "Call failed"; the other person: "Incoming call · 2:05", "Declined call", "Missed call", "Call failed"), can't be edited, forwarded, replied to or pinned, is deleted like any message, and stays out of search. The server stores and relays it like any other post and can't tell it from one; in a chat with a message timer it disappears like every other message.
- **Relay credentials are short-lived and granted to a proven connection.** `call.relay { cid }` (7.1) hands a connection that holds the one-on-one chat a TURN credential for the relay; the person called asks for one only when they accept. Pages use `iceTransportPolicy: "relay"`, keep only relay candidates in their own description (with the related address blanked), drop every other candidate from the other side's and refuse one with no relay candidate or more than one distinct DTLS fingerprint (a bundled description repeats the same fingerprint under each media section, which counts once), or longer than 10000 characters. A relay candidate counts only over `udp` or `tcp` and at an IP literal (a name would be looked up by the browser through the system's DNS, relay policy or not), and `a=remote-candidates` is dropped; every relay address the other side names must be one the server offered this device in this call, and one of them the relay this device used (the caller checks before it takes the answer; the person called once it has its own, and ends the call if they differ). The server may list two relays (`HUSH_TURN_URLS`, grouped by host, IP literals: the first host the default, the second for the Americas): the caller picks by its own time zone (`America/*` and `Pacific/Honolulu` take the second) and hands WebRTC that host's URLs alone, and the person called allocates on the relay the offer's candidates already name, so one relay sees a call, the pick travels only inside the sealed offer, and the server learns nothing of it. The check is relaxed from "all of theirs are mine" so that a page which still gathers on every offered relay can talk to one that picked, and it keeps the purpose: no one can steer a device to a relay this server did not offer it. There is no direct fallback, in development either: a server without a relay answers `unavailable`. A credential lasts 15 minutes (`HUSH_TURN_TTL`): the relay checks it when an allocation is made and keeps the allocation past it, so it bounds a leaked credential, not a call.
- **The relay keeps addresses the way the rest of the service does: in memory, for the life of the session, never on disk, never in a log.** Relay credentials are rate-limited by the same hourly-salted address tag as everything else (9.4) and per account, and the account's daily relay name (7.1) lets the relay's per-user quota cap the allocations one account holds at once. The relay forwards only to itself (both ends of a call hold an allocation on it): every other peer address is denied, and a firewall rule keeps it to its own relay ports on the server's address. The relay sees both endpoints' addresses for the duration of the call, which is the same exposure adversary A2 already has for every WebSocket, and no more. Media bytes passing through it are end-to-end encrypted by WebRTC (DTLS-SRTP); the relay cannot read them.
- **Group calls are not promised by this section.** If they come, they come through the same relay and the same sealed signaling; nothing here should be read as a design for them.

### 16.3 What stages 1 to 9 must not do

Each of these is a door that an earlier stage could close by accident. They are constraints on that stage, not work for it.

| Stage | Must keep | Because stage |
|---|---|---|
| 7 to 9 (media, kept from stage 6) | Pieces stay opaque: no content type, duration or kind, in the row or the path. Limits stay in the one `MEDIA_LIMITS` block. The post size limit (64 KB) is not lowered, since posts carry the sealed media descriptors. | Audio must stay indistinguishable from other media. |
| 7 to 9 (hardening) | The firewall list in 11.2 is configuration. Alerting, intrusion checks and the systemd unit must not assume the Node process is the only listener or that 443 is the only open port. | 10 adds a UDP relay listener. |
| 7 to 9 (hardening) | The no-address rule in 11.1 is written for the service, not for one process: any component added later, relay included, inherits it. | 10's relay would otherwise be the first place addresses could leak. |
| 7 to 9 (operations) | The deployment layout in 11.4 leaves room for a second service unit and its own config under `/etc/hush/`. Caddy is not assumed to front every listener. | 10's relay is a sibling of Node, not a route through Caddy. |
| 5 and 7 (protocol) | The frame grammar reserves the `call.*` op family alongside `mail.*`. Nothing treats "every op is a document op" as a rule. | 10 hands out relay allocations over the same socket. |
| 4 and 5 (capability plane) | Signaling is sealed: no stage adds a server-side notion of "who is in a call" or a per-chat record type that the server can read (the call records of 16.2 are sealed and memory-only). | 10 keeps call metadata as invisible as message metadata. |
| 3 (identity) | Nothing ties a connection to a network address beyond the hourly-salted bucket. | 10's relay rate limits reuse that bucket and nothing else. |

### 16.4 Stage 8: locking down write access

Everything else in this document protects what the server stores. It counts for nothing if someone can change the code itself: an altered `app/ui.js` can send every key to a third party, and the pins of 12.1 only prove that the page a person received is the page the server meant to send. The code can be changed from three places, and there is one way for anyone to notice if it was. Each item is a box to tick before launch; none needs a code change.

**The developer PC and the backup copy of the code.** The code is written here and the server is reached from here, so this is the first place to protect.

- [ ] The Windows account has a password or PIN of its own and locks itself after a few minutes away; nobody else uses it. Windows Hello is fine. What matters is that nobody can sit down at an unlocked session.
- [ ] The drive is encrypted (BitLocker, or device encryption on Home editions), so a lost or stolen PC does not hand over the code, the SSH key and the signed-in sessions.
- [ ] The SSH private key that opens the server has a passphrase, lives only on this PC, and is never copied into the backup of the code.
- [ ] The backup copy of the code (GitHub, or wherever it lives) is private, and the account that owns it has two-factor sign-in on, with the recovery codes written down and kept offline. Where the service allows it, password-only sign-in is turned off.
- [ ] Only the owner can write to that copy: no collaborators with push access, no deploy tokens, no integrations that can push. `git pull` on the server reads this copy (11.4), so whoever can write to it can change what runs.
- [ ] The email account behind the backup service and the Hetzner account has two-factor sign-in too, since password resets arrive there.

**The Hetzner server.**

- [ ] SSH accepts keys only: `PasswordAuthentication no`, `PermitRootLogin no`, `KbdInteractiveAuthentication no`, one named admin user with `sudo`. If the owner's own address is fixed, `ufw` limits port 22 to it.
- [ ] The firewall allows 80 and 443 to everyone, 22 for SSH, and nothing else (`ufw default deny incoming`), as in 11.2. Hetzner's own firewall in the Cloud Console repeats the same list, so a slip on the box is caught by the second one.
- [ ] Security updates install themselves (`unattended-upgrades`, with a reboot window at a quiet hour), and the owner looks at `apt list --upgradable` now and then for anything held back.
- [ ] The service runs as `hush`, a user with no shell and no password, under the systemd unit of 11.2 (`ProtectSystem=strict`, `NoNewPrivileges=yes`, `ReadWritePaths=/var/lib/hush`).
- [ ] The app's files are read-only to the app: `/opt/hush/server` and `/srv/hush/www` are owned by root, mode 755; `hush` and Caddy can only read them; only `/var/lib/hush` is writable by `hush`. So even a bug in the service cannot change the code the next visitor is served.
- [ ] Nothing else runs on the box: no panel, no second site, no database reachable from outside. `ss -tlnp` shows Caddy on 80 and 443, Node on `127.0.0.1:8080`, SSH, and nothing more.
- [ ] Releases happen only over SSH from the developer PC (`git pull`, then `systemctl restart hush`, 11.4). There is no web-based deploy hook.

**The Hetzner account.** Whoever holds it can open a console on the server, reset its root password or copy its disk, so it is a way around every item above.

- [ ] A strong password used nowhere else, kept in a password manager.
- [ ] Two-factor sign-in turned on (an authenticator app, not SMS), with the recovery codes kept offline next to the backup service's.
- [ ] One account, one owner: no shared logins, and no project members who do not need access.
- [ ] The rescue console and the password reset are the account's superpowers; the owner treats the account like the server's root key.

**Release transparency.** The items above keep outsiders out. This one lets anyone check that it worked, and lets them check on the owner too.

- [ ] Every release publishes the SHA-256 of its `index.html`, with the date and the release name, somewhere the server cannot quietly rewrite: the release notes in the code's repository, or any other place the owner already announces releases. Because `index.html` carries an `integrity` attribute for every file it loads (12.1, 10.6), that one hash pins the whole app: a changed `app/ui.js` would not load under the published page, and a changed `index.html` would not match the published hash.
- [ ] Anyone can verify what they are served: `curl -s https://<domain>/ | sha256sum`, or save the page from the browser and run `certutil -hashfile index.html SHA256` on Windows, then compare with the published value. The privacy statement (section 15) gets a line saying this exists and where the hashes are.
- [ ] The published list is only ever added to, never edited. A hash that changes without a new release line is the signal that something on the server was changed.

### 16.5 Native build (Capacitor, iOS)

The App Store version wraps the same page: `index.html`, `app/` and `vendor/` become the web assets of a Capacitor project and run in WKWebView. Nothing is rewritten for it.

**What stays the same.** The whole page and its script files, the adapter and the protocol, every key, every piece of encryption, the server. The sealed store (12.2) works as is: WKWebView gives the app its own `localStorage` and IndexedDB inside the app container, so the device key lives there; for the launch build the blob may move to the Keychain through a Capacitor plugin, which only changes where `hush:sealed` is read and written, not what it holds. Face ID in front of the lock gate is the one addition the lock screen has been waiting for.

**What changes.**

- **Server address.** The app loads the live page from `https://<domain>` (Capacitor `server.url`), so the page's origin is the site's own: `app/config.js` leaves `server` empty and the page connects to its own host, and the policy's `connect-src` lists `wss://<domain>`. `npm run csp` pins the file as usual. (A build that bundled the page locally would load from `capacitor://localhost` and need the address in `app/config.js`.)
- **Origin.** WKWebView sends the site's own `Origin`, so `HUSH_ORIGINS` names the site; a `capacitor://localhost` entry is only needed for a locally bundled page. Nothing else on the server changes.
- **File picker.** `<input type="file">` works in WKWebView for photos, videos and files; the album picker and the camera sheet open natively. Where the system picker falls short (several videos at once, the camera roll's originals), the Camera and Filesystem plugins hand back the same `File` objects and the rest of the media path (7.7) is unchanged, including "never re-encode video".
- **Camera and microphone.** `getUserMedia` works in WKWebView from iOS 14.3 with the usage strings in `Info.plist`, so voice messages and the in-app QR scanner run as they do on the web; the Camera plugin is the fallback for photo capture.
- **Push.** Push arrives through APNs via the Push Notifications plugin, and the only thing a push may carry is "something is waiting": no sender, no chat, no text. The server knows the recipient of a mailbox note, so a note can wake a device; a message in a chat cannot name a member, so a push for it would need a per-chat registration under the chat's side-channel tag (5.3), which is a design for a later stage, not a change to this one. Until then the app refreshes on open, as the web page does. The one exception is the call wake-up (`POST /wake`): its VoIP push carries a random mark and a tag derived from the wake ticket and that mark (HMAC-SHA256 of the mark under the key SHA-256("hush-wake-name" ‖ ticket), base64url, the first 22 characters), never the ticket itself, which is a bearer token; the tag differs on every push, so Apple sees nothing stable across calls from the same contact. The phone that issued the ticket names the caller from its own table of tickets; the server, which reads the ticket to find the phone, learns nothing it did not already know. From release 65 a second ticket kind, `m`, nudges a closed iPhone about a one-on-one message through the same `POST /wake`: an alert push to the device's alert token (`push.set` with `kind: "alert"`, kept in `apush` apart from the VoIP token) whose whole payload is `{"aps":{"alert":"New message","sound":"default"}}`, no name, text, chat id or badge, through per-ticket rate buckets of its own so a chatty contact can never silence calls; the per-address bucket is one for every kind and is spent before the ticket is read, so the one refusal said out loud tells nothing about a ticket. From release 93 a call ring also spends two buckets of its phone's, keyed by the account and device the ticket resolves to, whichever tickets ring it: `wakePerMinPerDevice` 4 a minute and `wakePerHourPerDevice` 30 an hour. They are spent only for a call ticket (kind `c`), only after the ticket resolves to a device with a VoIP token, and only after the ticket's own buckets (3 a minute, 20 an hour) have passed. A message nudge and an unknown, revoked or token-less ticket never touch them. A refusal there is as silent as the others: 204, no push, nothing said about the ticket or the phone. Both numbers sit above one ticket's, so one contact alone can never use a phone's allowance up, and another ticket of the same phone still rings. The trade-off is that two or more tickets for one phone (two accounts, at 20 an hour each) can use up its hour and silence its other callers until it refills. The buckets live in memory only, are never written or logged, and are forgotten by the hourly sweep once idle. The ticket reaches the contact inside the chat, as a call ticket does, so the server still registers nothing per chat. In a chat with a message timer the ticket's hidden message expires `ttl` after it is sent, counted from the server's clock (the message itself is dated just before the chat's latest, so nothing moves), and the page sends the same ticket again, at most once a load, once that message has expired, so a contact away longer than the timer still receives it. A push address belongs to one account and device, the latest to register it, so a phone that switches accounts takes its pushes along; whoever holds a token may register it, so a token is treated as a secret, never returned by any operation, and a move is logged as a count and nothing else.
- **Build identifier.** The app's half (CallAudio, CallPush, the shell) changes only when a new build is installed, while the page is served fresh on every launch, so the page must know which build it meets. From the build after release 84 the shell injects `window.hushBuild = { v, n, api }` at document start, main frame only (`v` the marketing version, `n` the build number, `api` a whole number the build bumps by hand when a method's name, payload or behaviour changes in a way the page must know; it lives in Info.plist as `HushApi`). The page keeps the oldest level each feature works with (`NATIVE_API`, calls: 1, the page-keeper build) and raises a level only in a page release after the build it needs is on every phone. A build from before `hushBuild` is read from the methods it lists (`mark` marks level 1). On a build too old for calls the page shows a notice in the chat list that stays until the app is updated ("Update Hush to keep making calls", a tap opens the TestFlight page now and the App Store at launch), refuses to place a call, and answers an offer with `end { reason: 'old' }` so the caller reads why at once. The level gates only this device's own behaviour: no key, permission or server state depends on it, and the server never sees it.
- **Native video (the app, from build level 3).** Inert until the build declares `hushBuild.api` 3 and lists `setVideo` (`natVideo()`); below that the page keeps the 16.2 shim and calls stay voice. The plugin contract: `start` takes `video: true` (negotiate the one video line: the caller's offer carries it, the callee's answer takes an offer's line) and `videoCall` (CallKit `hasVideo`/`isVideo`: the caller chose "Video call", or the verified offer said `cam: 1`; such a call opens on the loudspeaker unless headphones or Bluetooth are in use, and stays there when a camera goes off; a voice call opens on the earpiece); `setVideo({on, facing: "front"|"back", preview?})` → `{on, facing}`, rejecting `NotAllowedError` when the camera is denied (from build level 4, `preview: true` on an outgoing call only: the camera runs at once for this screen, before any audio, with nothing on the line; the plain On the page sends after the answer puts it on the line; before the answer nothing can be sent anyway: there is no remote description, no ICE and no track on the sender), and called only from this side's own tap or a video call's start (the caller's "Video call" after the answer, the callee's answer to a `cam: 1` offer; or the one automatic try again after a poor link turned this side's camera off; the plugin holds an On until the call's audio runs, so the app's "Video call" sends its offer with `cam: 1` at once and asks for the camera after the answer, and while it rings out its Video key is that choice, which a tap changes); `switchCamera()` → `{facing}`; `setLayout({remote, local})`, each `{x, y, w, h}` in CSS pixels or null to hide, the smaller rectangle drawn on top; `setPip({on})` → `{supported}`; `update` takes `video` for a ringing pushed call; `stats` adds `vIn {w, h, fps}` and `vOut {kbps, limit, h, loss}` (the drop rule reads these), and from the build after release 89 the figures Settings → Advanced shows: `vOut {w, fps, tgt, rc, codec, enc, bwe}`, `vIn {kbps, codec, drop, frz}`, `vCam {w, h, fps}` while the camera runs and `vTier {w, h, fps, kbps, wifi, full, lv, heat}` while it sends (numbers and short checked strings only: nothing that names a call or a person); a camera going on the line on Wi-Fi starts the bandwidth estimate at 2 Mbit/s, and two such iPhones negotiate H.264 Constrained High (640c), browsers and older builds Constrained Baseline; the `state` event adds `video {local: off|on|paused, facing, remote: none|live|stalled, pip}`. The plugin draws both pictures natively behind a transparent web view; the page's two video elements stay empty and give their rectangles, and while a picture shows the page clears only the call screen and what lies under it (`call-native-video`), keeping the call screen's colour around this side's picture when the far side's is not showing. Whenever the call screen is minimized, ends, or anything stands above it (a lock, a sheet, the photo viewer: z-index 20 or more; the call-mode lock stands below it by design), the page sends `setLayout` with both null and turns picture in picture off; those layers paint opaque anyway. Picture in picture turns on when the app goes to the background with the far side's picture live, off when it comes back. The marks, the consent rules, the drop rule and the chat entry are the browser's (16.2); the floating thumbnail is the browser's picture in picture and sits under every lock.
- **Release transparency.** The hash published for a release (16.4) is of the `index.html` inside the app bundle too; the App Store build is made from the same files and says which release it carries.
